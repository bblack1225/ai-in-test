# 目前系統裡所有的判定邏輯清單

> 照執行順序分五個階段整理：解析 → 爬蟲候選判定 → 互動安全判定 →
> 退回/復原判定 → 定位階段判定（測案執行時）。每項附「做什麼」跟「為什麼」。

最後更新：2026-09-20

---

## A. 解析階段（建立元件清單，`capture_screen_map.py`）

1. **visible 過濾**——只排除「當下真的沒被畫出來」的節點，其餘一律收錄。
   為什麼：不用 class 白名單提早篩選，避免像 Android 版早期那樣過度篩選漏資料。
2. **座標合法性檢查**——x/y/width/height 解析失敗就跳過這個節點。
   為什麼：沒有合法座標的節點沒辦法疊框、沒辦法點擊，收錄了也沒用。
3. **真原生ID判定**——`name` 存在且不等於 `label` 才算真的識別碼，否則視為
   系統把顯示文字回填進 `name` 的假象。
   為什麼：避免把「文案一改就變」的不穩定值誤用成穩定識別碼。
4. **截圖保護偵測**——判斷截圖是不是被系統擋成單一顏色。
   為什麼：決定後續 LLM 描述要不要送圖，被擋就改純文字判斷。
5. **指紋組成與雜湊**——沒有真識別碼的元件，用 class/顯示文字/九宮格位置/
   同層排序/鄰近文字五項組合後算雜湊值當識別碼。
   為什麼：在「精準區分元件」跟「小改版還能維持不變」之間取平衡。
6. **同次掃描碰撞偵測**——同一次掃描算出重複識別碼，自動加編號後綴。
   為什麼：保證單次掃描結果裡不會有兩個元件共用同一個識別碼。
7. **native_id 重複降級**（這次新補）——同畫面同 (class, native_id) 出現超過
   1次，全部降級成無識別碼，改走指紋。
   為什麼：處理清單裡每一列共用同一個識別碼的情況，避免多個元件互相覆蓋。
8. **可捲動內容偵測**——判斷畫面有沒有可以捲動的區域。
   為什麼：決定要不要啟動邊捲邊抓，單畫面快照可能漏掉捲動裡的內容。
9. **捲動到底判斷**——連續兩輪捲動後讀到的內容一致，視為已經捲到底。
   為什麼：iOS 沒有系統級的「這次捲動有沒有真的移動」回報可用，只能退而
   求其次用內容比對；已知弱點是遇到超大元件可能誤判提早到底。
10. **畫面穩定判斷**——連續兩輪候選簽章一致，才視為畫面內容已經穩定下來。
    為什麼：避免掃到「資料還在非同步載入中」的過渡畫面；可視情境關閉
    （報價類畫面永遠不會穩定，關閉可以省下大量等待時間）。

## B. 爬蟲候選判定（決定「要不要點」，`crawl_app_tree.py`）

11. **候選資格判定**——元件類型要符合特定類型清單，或是「看起來可以點的
    純文字」才算候選。
    為什麼：排除純粹用來顯示內容、不是操作用途的節點。
12. **常駐UI（chrome）排除**——畫面最上緣11%／最下緣88%的可點元件，加上
    底部導覽列本身，一律排除。
    為什麼：這些是到處都會出現的固定選單/導覽列，不是這個畫面獨有的內容，
    當候選探索沒有意義。
13. **危險字樣黑名單**——文字或識別碼命中「登出」這類字樣，永遠不點。
    為什麼：避免爬蟲不小心觸發會登出、造成真實後果的操作。
14. **候選去重**——同 class+顯示文字+座標的候選視為重複，只留一份。
    為什麼：畫面結構偶爾會把同一個元件回報兩次。
15. **疑似外部連結排除**——元件類型是連結，或文字含電話號碼/客服專線這類
    字樣，直接跳過不點。
    為什麼：點了很可能會跳出 App（撥號、開瀏覽器），不是這支 App 內部的
    畫面，探索了也沒意義還有風險。
16. **風險關鍵字排除**（預設關閉，選用開啟）——命中買進/賣出/刪單/轉帳
    這類字樣就跳過。
    為什麼：這類操作有真實金錢/帳務後果，預設保守，需要時才手動開啟。
17. **畫面外座標排除**——候選元件的中心點座標超出目前畫面高度範圍。
    為什麼：座標存在但實際上不在看得到、點得到的範圍內。
18. **同類型抽樣**——同一種樣式的候選（例如清單裡長得一樣的卡片）點過
    幾次都導向同一個畫面後，其餘的直接跳過。
    為什麼：避免對著大量同質性內容重複驗證同一件事，浪費時間。
19. **骨架簽章比對**——判斷這次看到的畫面，跟已經爬過的哪個畫面是同一個
    （或是全新的）。
    為什麼：只看結構特徵（不看會變動的資料內容），才能正確把「不同商品的
    同一種詳情頁」判定成同一個節點，不會各自炸出新畫面。

## C. 互動安全判定（點擊前後的檢查）

20. **彈窗偵測與處理**——偵測系統對話框或特徵字樣，分層處理：優先點掉
    確認性彈窗；找不到、看起來單純是資訊性彈窗才退而求其次點確定/OK；
    「登出/關閉App」這類危險字樣永遠不點。
    為什麼：彈窗會擋住畫面讓後續操作失效，但處理方式要保守，不能亂點。
21. **跳出App偵測**——點擊後偵測狀態是不是跑到 App 外（背景、或畫面context
    變成瀏覽器）。
    為什麼：確保爬蟲只探索這支 App 內部的畫面，跳出去要立刻拉回、不繼續
    探索外部內容。
22. **被登出偵測**——畫面上出現「重新登入/已登出/閒置過久」這類字樣，
    立刻中止整個爬蟲。
    為什麼：避免把登出後的畫面誤存進地圖，污染後續所有資料。

## D. 退回/復原判定（要離開一個畫面回到上一層時）

23. **退回策略鏈**——依序嘗試：點導覽列按鈕、點左上角按鈕、系統原生退回、
    從畫面左緣往右滑。
    為什麼：涵蓋不同 App 常見的「返回」實作方式，盡量提高成功機率。
24. **退回結果驗證**——每次嘗試退回之後，用骨架簽章確認是不是真的回到
    目標畫面，不是「動作做了就當作成功」。
    為什麼：點擊動作不保證真的達到預期效果，必須實測驗證。
25. **錨點復原**（新增，尚未驗證有效）——前面的退回策略反覆失敗後，改用
    根畫面自己「點了骨架沒變」的候選當錨點，先確認真的回到根畫面，
    才依照記錄的路徑重新點一次。
    為什麼：很多「畫面切換」其實是同一個畫面內部的顯示模式/分頁切換，
    根本沒有真正的「返回」可做，硬猜返回鍵反而會誤觸、越走越遠；
    改用已經驗證過會回到原地的候選當錨點，比亂猜更有機會成功。

---

## E. 定位階段判定（測案執行時，重新找到元件，`run_test_case.py`）

26. **自訂查詢優先**——人工或AI事先驗證存下來的查詢方式，優先於所有自動
    推導的方式使用。
27. **原生識別碼直接查**——有真識別碼的元件，直接用識別碼查找。
28. **精確條件查詢＋邊捲邊查**——沒有識別碼的元件，先用類型+文字精確查詢，
    查不到就邊捲動可捲動容器邊重新查詢。
    為什麼：長清單常見「畫面外的內容在結構裡整個消失」（cell重用），
    需要捲到那個位置附近才查得到。
29. **鄰近文字錨點消歧義**——精確查詢查到多個結果時，改用鄰近文字定位到
    唯一的錨點，再挑座標最接近錨點的候選。
    為什麼：處理清單裡「每一列都有一個文字相同的按鈕」這種情境。
30. **座標點擊備援**——上面所有方式都定位不到，退回用掃描當下記錄的座標
    直接點擊。
    為什麼：最後手段，確保至少有個動作可以執行，但精準度最低、最容易
    因為畫面版面變動而點錯。
