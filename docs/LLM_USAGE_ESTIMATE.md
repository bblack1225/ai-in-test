# LLM 使用量估算

> **模型與單價以 `config.py`（`LLM_MODEL`／`LLM_MODEL_PRO`，可在 `config.toml` 的 `[llm]` 覆寫）為準**，
> 本文的模型名稱與金額是 2026-09 的估算，只用來抓量級。

> 盤點目前這套系統裡，LLM（Gemini，`LLM_MODEL = "gemini-flash-latest"`）
> 在哪些時機被呼叫、大概花多少 token／多少錢。金額用 Gemini 2.5 Flash
> 公開定價換算（輸入 US$0.30／百萬token、輸出 US$2.50／百萬token），
> `-latest` 別名實際解析到的模型可能不同，價格僅供抓量級參考。

最後更新：2026-09-17

## 一、LLM 在哪些時機被呼叫

| # | 呼叫點 | 觸發時機 | 送了什麼 |
|---|---|---|---|
| 1 | `describe_native_elements()`（`capture_screen_map.py`） | 掃描一個畫面、`describe=True`、且畫面上有原生ID元件時 | 該畫面**所有原生ID元件**的 class/label/value（純文字，無截圖），一次批次呼叫 |
| 2 | `describe_generated_elements()`（`capture_screen_map.py`） | 掃描一個畫面、`describe=True`、且畫面上有無ID元件時 | 該畫面**所有無ID元件**的 class/label/bounds/position_bucket/nearby_text ＋ 該畫面截圖（除非螢幕保護擋掉，改純文字），一次批次呼叫 |
| 3 | `/agent_xpath`（`viewer_server.py`，「AI定位」按鈕觸發） | 人工在 viewer 上對某個定位失敗的元件按下「AI定位」 | **完整的畫面 page_source（原始XML樹）**＋目標元件線索，最多重試 3 次，**每次重試都重送一次完整 page_source** |
| 4 | `/llm_chat`（`viewer_server.py`，「LLM測案產生」對話框） | 使用者在測案產生對話框裡每送一則訊息 | 完整 system prompt（含使用者選定畫面的精簡元件資料）＋**到目前為止的完整對話歷史**，無狀態設計，每輪都整包重送 |
| 5 | `generate_test_case.py`（已移除） | 命令列單獨執行（較早期的 POC，已被 3 的對話式產生取代） | 單一畫面的精簡元件清單 |

**關鍵：1、2 是「掃描階段」的成本，按畫面數計；3、4 是「人工互動階段」的成本，按操作次數／對話輪數計，且都有「整包重送」的設計，用越多次/對話越長，單次成本不會降反而可能持平或略增。**

## 三、還沒實測、用估算的地方

### 呼叫點 #3：`/agent_xpath`（AI定位）

沒有實測過（這次連線的裝置還沒用過這個按鈕）。用已知數字推算：

- 這次自選庫存畫面的 `page_source` 實測長度是 **97,965 字元**
- 抓一個保守的中英混合 XML 文字 token 比例（約 3 字元 ≈ 1 token），單次 page_source 換算約 **32,000～33,000 tokens**
- 每次重試都重送完整 page_source，最多 `AGENT_XPATH_MAX_ATTEMPTS = 3` 次

| 情境 | 概算 input tokens | 概算 total | 概算金額 |
|---|---|---|---|
| 第1次就成功 | ~33,000 | ~33,150 | US$0.010（~NT$0.3） |
| 重試到第3次才成功/放棄 | ~99,000 | ~99,450 | US$0.030（~NT$1） |

**這是目前系統裡單次成本最高的操作**，因為送的是完整原始樹，不是精簡過的資料。畫面元件越多（越深的頁面、越複雜的清單），`page_source` 越長，成本跟著線性增加。

### 呼叫點 #4：`/llm_chat`（LLM測案產生對話）

沒有實測過。用專案裡另一份文件（`ppt_prompt_llm_input_modes.md`）記錄的真實規模參考：22個畫面、681個元件，精簡後約 **12萬字元**（≈ 40,000 tokens）。

| 情境 | 概算 | 概算金額 |
|---|---|---|
| 單輪對話（假設選 2-3 個相關畫面，精簡資料較小，抓 1萬 tokens context） | ~1.1萬 input + ~1千 output | US$0.006（~NT$0.2） |
| 單輪對話（選了很多畫面，接近 12萬字元/4萬token 這種規模） | ~4萬 input + ~1千 output | US$0.015（~NT$0.5） |
| 10輪來回的完整對話（假設context規模不變，只是歷史逐輪變長，抓平均4萬input/輪） | ~40萬 input + ~1萬 output | US$0.145（~NT$4.7） |

**這裡的風險不是單輪貴，是「無狀態、每輪整包重送」的設計，對話越長，單輪的 input token 量只會增加不會減少**——因為每往前一輪，「到目前為止的對話歷史」就多一輪的量要重送。

## 四、抓量級：把整支 App 掃完＋描述，大概多少錢

假設整支 App 有 N 個畫面，每個畫面的無ID元件數、截圖大小跟這次自選庫存的樣本（14,789 tokens/畫面）差不多：

| 畫面數 N | 總token(估) | 金額(美金) | 約新台幣 |
|---|---|---|---|
| 10 | ~15萬 | ~$0.11 | ~NT$3.5 |
| 50 | ~75萬 | ~$0.55 | ~NT$18 |
| 100 | ~150萬 | ~$1.10 | ~NT$35 |

**結論跟上次口頭講的一致：純粹「掃描+描述」這件事，錢便宜到可以忽略，真正的成本瓶頸是時間（LLM 往返等待），不是花費。**

如果流程裡還會用到「AI定位」「LLM測案對話」，這兩個才是真正會把總花費拉高的地方，尤其是 AI定位在複雜畫面上重試、或測案對話拉得很長的時候。

---

## 五、如果要控制成本，值得做的兩件事（先記錄，不是現在就要做）

1. **`/agent_xpath` 送精簡過的 tree，不要送完整 page_source**——例如只送目標元件附近幾層的子樹，而不是整個畫面的 XML，可以大幅降低單次成本，尤其是複雜畫面
2. **`/llm_chat` 考慮限制/裁剪對話歷史長度**，或把「使用者選定的畫面精簡資料」跟「對話歷史」分開快取，不要每輪都整包重送不會變動的畫面資料部分

這兩點都還沒做，先記錄在這裡，之後真的覺得成本或延遲是問題時再回來處理。
