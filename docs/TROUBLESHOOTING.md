## 詳細說明

### 1. Xcode 授權條款未同意

**現象**：`xcrun xctrace list devices` 報錯
`You have not agreed to the Xcode license agreements.`

**原因**：裝完 Xcode.app 並用 `xcode-select -s` 指向它之後，還需要另外同意授權條款，
光是能執行 `xcodebuild -version` 不代表授權已同意。

**解法**：
```bash
sudo xcodebuild -license accept
```

**會不會再發生**：不會。這是 Mac 這台機器的系統層級設定，同意一次之後，
之後不管測哪個 App 都不會再跳出來，除非重灌 Xcode 或换 Mac。

---

### 2. `sudo` 指令需要互動式終端機

**現象**：透過 Claude Code 執行 `sudo xcode-select -s ...` 時報錯
`sudo: a terminal is required to read the password`

**原因**：Claude Code 的指令執行環境不是完整互動式終端機，沒辦法接收密碼輸入的提示。

**解法**：改由使用者自己在 Terminal（或用 `!` 前綴）手動執行需要密碼的指令。

**會不會再發生**：跟測試哪個 App 無關，只要是需要 `sudo` 密碼互動輸入的指令都會遇到，
之後預期不會再需要用到 sudo（設定都已完成）。

---

### 3. WebDriverAgent 預設 Bundle ID 衝突

**現象**：Xcode 編譯 `WebDriverAgentRunner` 時報錯
`No profiles for 'com.facebook.WebDriverAgentRunner' were found`

**原因**：WebDriverAgent 是 Facebook（Meta）開源的專案，原始碼裡預設寫死的 Bundle ID
是 `com.facebook.*`，這個命名空間只有 Facebook 自己的開發者帳號能簽署，
別人用自己的 Apple ID 一定簽不過。

**解法**：把 `WebDriverAgentRunner` target 的 Bundle Identifier 改成自己專屬的字串，
例如 `com.cfhtest001.WebDriverAgentRunner`。

**會不會再發生**：不會。WebDriverAgent 是 Appium 用來跟 iOS 系統溝通的中介服務，
跟你實際要測試的目標 App（例如公司自己的 App）完全無關，
這個專案簽署設定好一次，之後測任何 App 都是共用同一個 WDA，不用重改。

---

### 4. `IntegrationApp` target 缺少 Signing Team

**現象**：`Signing for "IntegrationApp" requires a development team.`

**原因**：WebDriverAgent 專案裡除了 `WebDriverAgentLib`、`WebDriverAgentRunner`，
還有一個附屬的 `IntegrationApp` target，沒設定 Team 一樣會擋住整個 build。

**解法**：跟 WebDriverAgentRunner 一樣，在 Signing & Capabilities 分頁選擇 Team
（Bundle ID 若也是 `com.facebook.*` 開頭也要一併修改）。

**會不會再發生**：不會，原因同第3點，屬於 WDA 專案一次性設定。

---

### 5. 手機信任狀態跑掉

**現象**：換了另一台手機測試，或手機重插 USB 後，`xcrun xctrace list devices`
把裝置列在 `Devices Offline`，或系統顯示「不受信任」。

**原因**：每台裝置第一次接上 Mac 都需要重新完成「信任這台電腦」的授權，
換手機、手機重置隱私設定、或某些系統更新後，這個信任紀錄可能會被清掉。

**解法**：
- 手機解鎖，確認有跳出「是否信任這台電腦」的彈窗並點「信任」
- 找不到彈窗就拔線重插
- 必要時到手機「設定 → 一般 → 傳輸或還原 iPhone → 還原 → 重置定位與隱私權」清掉舊紀錄，重新觸發信任彈窗

**會不會再發生**：**會**。這是「裝置」跟「Mac」之間的配對關係，
跟你測哪個 App 無關，但只要換新裝置、或既有裝置信任紀錄被清掉，就得重做一次。

---

### 6. 開發者憑證需在手機上手動信任

**現象**：Xcode 提示
`Verify that the Developer App certificate for your account is trusted on your device.`

**原因**：用 Apple Developer 憑證簽署安裝的 App（例如 WebDriverAgentRunner），
第一次安裝到某台手機時，iOS 系統預設不信任這個簽署身分，必須手動去信任。

**解法**：手機「設定 → 一般 → VPN 與裝置管理」，找到對應的開發者項目，點「信任」。

**會不會再發生**：**可能會**。如果之後測試的目標 App 是用**不同的 Apple Developer 帳號 / Team**
簽署安裝的（例如公司用付費帳號簽自己的 App，跟你簽 WDA 用的個人帳號不同），
那台裝置就需要**再信任一次那個不同的憑證**。如果目標 App 已經是透過 App Store
或既有流程安裝好的，則不會遇到這個問題。

---

### 7. 免費 Apple ID 簽署效期只有 7 天

**現象**（尚未實際發生，但 PROJECT_BRIEF 已提及）：
超過 7 天後，用免費帳號簽署的 App（包含 WebDriverAgentRunner）會過期失效，
需要重新用 Xcode 簽署安裝一次。

**原因**：Apple 對免費（非付費 $99/年）開發者帳號的簽署憑證，效期只有 7 天。

**解法**：效期到了之後，重新對 `WebDriverAgent.xcodeproj` 執行一次 `Cmd+U`
（Product → Test）即可重新簽署安裝。

**會不會再發生**：**會**，而且是週期性的，跟測哪個 App 無關（WDA 本身也會過期）。
如果之後升級成付費帳號（$99/年），效期會延長到 1 年，可以大幅降低這個問題的頻率。

---

### 8. `GEMINI_API_KEY` 讀不到

**現象**：`ValueError: No API key was provided`，即使已經寫進 `~/.zshrc`。

**原因**：zsh 預設**只有互動式 shell 才會載入 `.zshrc`**，Claude Code 執行指令用的是
非互動式 shell，讀不到裡面 export 的環境變數。

**解法**：執行腳本時改用 `zsh -i -c '...'` 強制以互動式模式載入設定檔。

**會不會再發生**：不會（已確認解法有效，且是工具執行方式的問題，跟測哪個 App 無關）。
如果之後直接在自己的 Terminal 手動執行（不透過 Claude Code），本來就不會遇到這個問題。

---

### 9. Gemini 模型 `gemini-2.5-flash` 已停用

**現象**：`404 NOT_FOUND ... This model models/gemini-2.5-flash is no longer available to new users`

**原因**：這隻 API key 是新申請的，Google 對新用戶關閉了這個舊模型的存取權限。

**解法**：改用 `gemini-flash-latest`（Google 維護的別名，自動指向目前建議的 flash 模型，
比寫死特定版本號更耐用，減少之後又被停用的機率）。

**會不會再發生**：不會，已修正在程式碼裡，跟測哪個 App 無關（這是 LLM 描述那一段的共用邏輯）。

---

### 10. Gemini API 503 暫時性過載

**現象**：`503 UNAVAILABLE ... This model is currently experiencing high demand.`

**原因**：Google API 端暫時性流量過載，不是設定問題。

**解法**：重跑一次指令即可（第二次就成功了）。

**會不會再發生**：**偶爾會**，純粹是 Gemini API 端的隨機狀況，
跟裝置、跟測哪個 App 完全無關，之後每次呼叫都有小機率遇到，重試即可。
如果之後頻率變高，可以考慮在程式碼裡加簡單的重試機制（目前 POC 階段先不處理）。

---

### 11. 截圖裁切座標對不上（Retina 縮放比例）

**現象**：`crop_element_screenshot()` 裁出來的截圖跟預期元件位置對不上，
其中一張甚至整張是空白。

**原因**：Accessibility Tree 回報的 `bounds` 是「point」座標（邏輯座標），
但 `driver.get_screenshot_as_png()` 回傳的是「pixel」座標（實際像素）。
測試用的 iPhone 14 是 3 倍 Retina 螢幕：
`get_window_size()` 回傳 390×844（point），實際截圖卻是 1170×2532（pixel），
兩者差了整整 3 倍，直接拿 point 座標去裁 pixel 圖片當然會裁錯位置。

**解法**：在 `scan_screen()` 裡動態算出縮放比例
（`螢幕截圖像素寬 / window_size 寬`），裁切前把 bounds 乘上這個比例
（詳見程式碼 `crop_element_screenshot()` 的 `scale_x` / `scale_y` 參數）。
`bounds` 欄位本身（存進 JSON、給 Appium 互動用的座標）維持原本的 point 座標不變，
只有裁切截圖這個步驟需要換算。

**會不會再發生**：不會。因為縮放比例是**每次掃描當下動態計算**出來的，
不是寫死某個機型的固定倍數，所以換成任何 iPhone 型號（2x 或 3x 縮放都一樣）、
或換測任何 App 的畫面，都會自動套用正確的比例，不需要再手動調整。

### 12. 資料已存檔成功，但收尾 `driver.quit()` 仍報錯

**現象**：終端機印出「完成，共產出 N 筆元件資料 / 已儲存至 element_map.json」，
但緊接著又跳出一段 `InvalidSessionIdException: A session is either terminated or not started`
的 Traceback，整個指令 exit code 是 1（視覺上像是失敗了）。

**原因**：`element_map.json` 是在 `scan_screen()` 成功回傳後就立刻寫檔完成，
寫檔動作已經結束。錯誤是發生在**寫檔之後**的 `finally: driver.quit()`——
如果這次掃描前面（尤其是 WDA 啟動）花了比較久的時間，Appium/WDA session
可能因為閒置過久被系統判定逾時、提早關閉，導致最後想「正常關閉連線」時
連線其實已經不在了，才跳出這個例外。

**解法**：不用特別處理，先檢查 `element_map.json` 裡有沒有這次的畫面資料
（`python3 -c "import json; print([s['screen_name'] for s in json.load(open('element_map.json'))['screens']])"`），
只要資料有進去就代表這次掃描其實是成功的，可以忽略這段收尾錯誤繼續往下做。

**會不會再發生**：**可能會**，尤其是整體流程耗時較久的那次掃描（例如 WDA 剛好需要重新建置）。
跟測哪個 App 無關，純粹是收尾階段的時序問題，不影響資料正確性。

### 13. 同一個 native_id 出現在不同 class 上，unique_id 互相覆蓋

**現象**：實測你好證券 App 的 `login_screen` 時發現，「忘記密碼」「不登入先逛逛」
「02-1234-5678」這幾個文字，各自都同時是一個 `XCUIElementTypeButton`
跟它內部的 `XCUIElementTypeStaticText` 的 `native_id`（iOS 常見的「按鈕包著文字」結構，
兩層都各自有 accessibility name，且都通過元件篩選條件）。

**原因**：原本 `make_native_unique_id()` 只用 `screen_name + native_id` 組
`unique_id`，沒有把 `class` 算進去，導致這種「同名不同 class」的情況會產生
一模一樣的 `unique_id`，違反 PROJECT_BRIEF 設計決策2「每個元件一個可長期追蹤的
唯一 ID」的前提。連帶地，`describe_native_elements()` 用 `native_id` 存
LLM 回傳描述的查找表也有一樣的碰撞問題，會讓其中一個元件的描述被另一個蓋掉。

**解法**：
- `unique_id` 格式改成 `{screen_name}::native::{class}::{native_id}`（多插入 class 這一段）
- LLM 回傳描述的查找 key 也改用 `class::native_id` 組合，避免互相覆蓋

> ⚠️ **注意**：這跟 `PROJECT_BRIEF.md` 裡「唯一 ID 規則」表格寫的格式
> （`{screen_name}::native::{native_id}`，例如 `login_screen::native::username_field`）
> 不一致了，是實測後發現原設計會漏掉一種碰撞情況才修正的。
> 如果要更新 PROJECT_BRIEF.md 那份表格，或是有不同的處理方式（例如直接濾掉
> 按鈕內部的子文字元件），麻煩再跟我確認。

**會不會再發生**：不會（邏輯已修正，同一個 native_id 不管出現在幾種不同 class
上都會各自產生獨立的 unique_id），跟測哪個 App 無關，是元件 ID 產生邏輯本身的修正。

### 14. `name` 只是文字回填，不是真正的 accessibilityIdentifier

**現象**：直接印出 login_screen 的原始 Accessibility Tree XML 後發現，
17 個候選元件裡有一大半的 `name` 是中文，而且**跟 `label`/`value` 完全一樣**
（例如 `name="忘記密碼" label="忘記密碼" value="忘記密碼"`）。
只有 5 個是英文（`loginbutton`、`loginidfield`、`loginpassfield`、
`loginremeberbutton`、`ic24PxGreyEyesClosedNsp`），且都跟 `label` 不同。

**原因**：iOS 在開發者**沒有明確設定 `accessibilityIdentifier`** 的情況下，
系統會自動把該元件顯示的文字回填進 `name` 欄位。原本的判斷邏輯只看
「`name` 是不是空的」，把這種「文字回填」也當成「有 native id」，
但這種 id 其實**不穩定**——UI 文案一改（多語系、文案調整），這個「id」就會跟著變，
違反 PROJECT_BRIEF「可長期追蹤的唯一 ID」的設計初衷。

**解法**：`parse_candidate_elements()` 新增判斷：`name != label` 時才算「真正的
native id」（`is_real_native_id`），`name == label` 一律視為沒有 native id，
改走 fingerprint hash 那條路（跟沒有 id 的元件一樣，會產生截圖裁切、用 LLM
看圖推論用途）。

**會不會再發生**：不會，邏輯修正後對任何 App 都適用——只要該 App 的開發者
也沒有明確設定 `accessibilityIdentifier`，這個判斷就會正確地把它歸類到
「無 id」而不是誤判成「有 id」。**這也代表之後同一支 App 如果補上了明確的
`accessibilityIdentifier`，該元件會從「無id」自動變成「native」，這是預期內的行為。**

### 15. 純圖示按鈕（沒有 Button 外殼）完全抓不到——已擴大候選範圍納入 Image

**現象**：你好人壽「保單總覽」頁的客服圖示（`ic_customService`）、通知鈴鐺
（`ic_messageNotice`），兩個都是 `XCUIElementTypeImage`，而且外層也沒有任何
`Button` 或其他可互動 class 包著，完全被 `INTERACTIVE_CLASSES` 白名單排除，
不會出現在候選清單裡（跟之前「密碼欄眼睛圖示」不同，那個好歹 class 是 Button）。

**原因**：`INTERACTIVE_CLASSES` 原本沒有把 `XCUIElementTypeImage` 算進去，
因為多數圖片是純裝飾用（背景、插圖、Logo），但這代表**用「圖片+手勢辨識」
做的純圖示按鈕**（沒有包成 Button 的那種）會被完全漏掉，即使它們可能是重要的
互動入口（例如通知鈴鐺）。這類元件本身可以正常被 XPath/accessibility id
定位並點擊（`accessible="false"` 只影響 VoiceOver 焦點，不影響 XCTest
能不能對它送出觸控事件），問題純粹出在我們工具的篩選階段，不是定位技術限制。

**解法**：把 `XCUIElementTypeImage` 加進 `INTERACTIVE_CLASSES`，並在
`describe_generated_elements()` 的 LLM 呼叫裡，對這批新增的圖示候選多問一題
「一般使用者看到這個圖示，會不會預期它可以點擊觸發功能」（`is_likely_interactive`），
只有判定為可互動的才正式收錄進元件清單；已經有 `name != label` 的圖示
（像 `ic_messageNotice` 這種）直接當 native 元件處理，不需要 LLM 判斷。

**先暫緩、記錄下來之後再討論的優化項目**：
1. **候選前先用尺寸粗篩**（例如只收 12-60pt 這種典型圖示尺寸），目前先不做，
   所以背景圖、大張插圖等也會先進候選清單，讓 LLM 判斷再篩掉，之後如果發現
   雜訊太多、成本太高，可以加這道程式碼粗篩
2. **`is_likely_interactive == false` 的候選要不要留紀錄**，目前選擇**不留**
   （判定不可互動就直接捨棄，不寫進最終 JSON），之後如果需要除錯/校對這批
   被排除的候選，可以考慮加一個獨立的排除清單檔案
3. **要不要限制只篩「功能性文字/區塊附近」的圖示**（縮小送進LLM的範圍），
   目前先不限制，所有 `visible=true` 的 Image 都送進去判斷

**會不會再發生**：解法對任何 App 都適用（只要用純圖片手勢做按鈕的模式），
但因為沒有做尺寸粗篩，畫面上圖片元件越多的畫面，LLM 判斷成本會越高，
這是已知取捨，等後續視實際使用量決定要不要加粗篩。

### 16. 水平/垂直捲動清單裡的元件座標超出截圖範圍，裁切時崩潰

**現象**：`ValueError: Coordinate 'right' is less than 'left'`，發生在
`crop_element_screenshot()`。你好人壽「健康吧」頁的「健康目標」是一個
可以左右捲動的清單，畫面截圖當下只拍得到目前顯示的部分，但 Accessibility
Tree 回報的元件座標**不受目前截圖範圍限制**（還沒捲到、或已經捲出畫面的
項目一樣有座標資料）。當元件座標整個落在截圖範圍之外時，裁切框的
右邊界會被夾到比左邊界還小，`PIL.Image.crop()` 直接丟例外讓整支程式崩潰。

**原因**：原本的裁切座標計算是 `min(image.width, x+w+padding)` 跟
`max(0, x-padding)` 分開算左右邊界，沒有考慮到「元件整個在畫面外」時
這兩個值可能反過來（右邊界被夾到比左邊界小）的情況。

**解法**：`crop_element_screenshot()` 改成回傳 `bool`，四個邊界都各自
獨立夾在 `[0, image寬/高]` 範圍內，算完後檢查 `right <= left` 或
`bottom <= top`，是的話直接判定「這個元件當下截圖拍不到」，不裁切、
不寫檔，回傳 `False`。呼叫端（`scan_screen`）改成：裁切失敗就印警告訊息，
JSON 裡該元件的 `screenshot_crop` 欄位存 `null`，其他資料照常寫入
（`description` 仍然是 LLM 看完整張截圖後推論出來的，不受影響，只是
沒有裁切特寫圖可以人工核對）。

**會不會再發生**：**會**，任何畫面只要有捲動清單、輪播、分頁等「畫面上
同時存在但當下截圖看不到」的元件結構，都可能觸發，但已經修成不會讓
整支程式崩潰，只是那幾個元件會缺一張裁切截圖可以核對。

### 17. Gemini API 429 配額用盡（跟503是完全不同的問題）

**現象**：
```
google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED.
Quota exceeded for metric: generate_content_free_tier_requests, limit: 20, model: gemini-3.7-flash
Please retry in 52.138198684s.
```

**原因**：跟已知問題10（503暫時性過載）**本質不同**——
- 503：Google 伺服器端容量問題，跟我們呼叫次數無關，隨時可能發生
- **429：這隻免費 API key 每天的請求配額用完了（目前上限20次/天/模型），
  是我們自己這個 session 密集掃描+ 多次503重試累積出來的，是可預期、
  跟用量直接相關的問題**

**解法**：等 API 回應建議的秒數（這次是52秒）之後重試。如果重試後還是
429，代表當下配額真的還沒恢復，需要等更久，或考慮升級成付費方案
（免費方案每天請求數上限低，密集測試/開發階段很容易撞到）。

**跟自動重試機制的關係**：`generate_content_with_retry()` 目前**只捕捉
`ServerError`**（503這類），429 屬於 `ClientError`，不會被誤判去重試——
這是刻意的，因為429重試也沒用（配額沒恢復重試一樣會429），亂重試只會
更快把「等待中」的配額額度耗光，直接讓例外拋出來、印出明確錯誤訊息，
比默默重試4次再失敗更清楚。

**會不會再發生**：**會**，而且是**用量越大越容易發生**，跟哪個 App、
哪個畫面都無關，純粹是這隻 API key 的每日配額問題。如果之後要密集測試
（例如一次掃很多畫面、或跑第二三步驟的LLM生成測試案例），建議留意
呼叫頻率，必要時間隔開執行，或評估升級付費方案。

### 18. 指紋不夠精細，同一次掃描內不同元件算出相同 unique_id

**現象**：你好人壽「健康吧」頁裡，「睡眠時數」跟「健身場館簽到次數」
兩個不同位置（`x=285` vs `x=399`）的佔位符文字「-」，指紋算出來完全一樣：
```json
{"class": "XCUIElementTypeStaticText", "label_text": "-", "position_bucket": "middle_right",
 "sibling_index": 0, "nearby_text": []}
```
導致兩筆不同元件的 `unique_id` 完全相同，JSON 陣列裡出現重複 id。

**原因**：這兩個元件都在「健康目標」橫向捲動清單裡各自獨立的小容器內，
`nearby_text`（同層兄弟節點文字）抓不到「睡眠」「健身場館」這些真正能
區分兩者的標題文字（不在同一層），`sibling_index` 也都剛好是0，
`position_bucket` 這種九宮格分區又太粗，三個線索同時失效才會完全撞在一起。
這比已知問題3（`sibling_index`/`nearby_text` 計算不夠精確）更進一步暴露出
指紋設計本身在「同一排重複排版結構」下的弱點。

**解法（先求「絕對不重複」這個底線，不動指紋演算法本身）**：`scan_screen()`
內用一個 `seen_unique_ids` 字典記錄這次掃描已經出現過的 unique_id，
碰到重複就自動加上編號後綴（`_2`、`_3`...），保證同一次掃描輸出的
`unique_id` 一定唯一。**真正從根本降低碰撞機率**（例如放寬 `nearby_text`
搜尋範圍到往上找一兩層），留給已知問題3一起處理，兩者病灶相同。

**會不會再發生**：**可能會**，尤其是同一排重複排版結構（例如清單裡好幾個
一樣長相的卡片，內容剛好都是預設值/佔位符）的畫面。已加上後綴保底機制，
不會再讓重複 id 流出去，但後綴本身沒有語意，只是保證唯一性的權宜做法。

### 19. App 閒置逾時自動登出，同名畫面重掃會覆蓋成登出畫面的資料

**現象**：討論/規劃花比較久的時間沒有實際操作手機時，你好人壽 App 會自動
跳出「太久沒動了喔，請您登出/關閉APP...」（錯誤代碼003）並登出。如果這時候
直接用原本的 `screen_name` 重新掃描，**會把該畫面原本正常的資料整個覆蓋掉**
（`save_to_json` 是同名畫面互相覆蓋，不是累加），造成明明前一次掃描是對的，
下一次卻莫名其妙變成只有2-4個元件、內容變成登出提示訊息。

**原因**：純粹是 App 本身的 session 閒置逾時機制，跟我們工具無關；
問題在於工具沒有能力自動判斷「手機現在到底在哪個畫面」，只能相信
使用者回報的畫面名稱，掃描前不會主動確認畫面內容是否吻合。

**解法**：掃描前**先截圖確認畫面內容**再執行（這個 session 後來養成的習慣），
發現是登出畫面就先重新登入、導航回目標畫面，再重新掃描。

**會不會再發生**：**會**，跟哪支 App、閒置多久觸發登出的門檻都不同，
如果討論/規劃時間拉長，建議掃描前一律先截圖確認畫面沒問題再執行，
避免辛苦掃到的資料被誤覆蓋。

### 22. 座標點擊備援機制在錯誤畫面上會誤觸元件卻回報 PASS（已修正）

**現象**：故意在錯誤畫面（健康吧）上執行保單總覽頁的測試案例，`assert_visible`
正確判斷元件不存在而 SKIP，但 `tap` 那步 XPath 一樣查不到（因為根本不在
對的畫面），卻還是退回座標點擊，用**舊畫面掃描當時記錄的座標**在**當前完全
不相關的畫面**上點了一下，還回報 `PASS`。事後回頭檢視，第一次「成功執行」
的那次，很可能也是同樣狀況（手機當下根本不在保單總覽頁，座標點擊剛好誤打
誤撞點出了反應），只是當時還沒發現，看起來像是正常成功。

**原因**：`run_test_case.py` 原本完全沒有檢查「手機現在是不是真的在測試案例
鎖定的那個畫面」，只要 XPath 找不到就默默退回座標，不管座標點到的到底是
不是原本要測的東西。座標本身只跟位置有關，跟「現在螢幕上顯示什麼內容」
完全無關，這是最大的風險——如果座標剛好對到別的畫面上一個有真實副作用的
按鈕（送出、刪除、確認等），會在完全不對的情境下誤觸發真實操作。

**解法**：新增 `verify_current_screen()`，執行測試步驟前，先用該畫面已知的
native id 元件當指紋，檢查目前手機畫面能找到幾個。過半數對不上就直接中止
執行（`SystemExit`），並存一張當下截圖方便排查，不會再悶不吭聲繼續跑。

**會不會再發生**：**會**，只要測試腳本執行時手機沒有先手動導航到正確畫面
就會觸發，但現在會被畫面校驗機制正確擋下，不會再誤觸操作、也不會再誤報成功。
**這個發現本身也證明了畫面校驗機制的必要性**：沒有它的話，永遠不會知道
某次「成功」其實只是僥倖。

### 23. XPath 命中但元件 `enabled=false`，程式仍直接點擊並回報 PASS（尚未修正）

**現象**：實測時「查看保單」按鈕透過 XPath 精準命中唯一結果，但印出的元件
屬性顯示 `enabled='false'`，程式仍照常呼叫 `.click()` 並回報 `PASS`，
沒有檢查這個元件當下是不是真的處於可互動狀態。

**原因**：`run_tap()` 目前不管是 native 還是 generated 元件，找到元件後就
直接呼叫 `.click()`，沒有先檢查 `is_enabled()`。點擊一個 `enabled=false`
的元件在 XCTest 底層通常不會有實際效果（等於白點一次），但程式無從得知，
一樣回報成功。

**解法（尚未實作）**：`run_tap()` 應該在點擊前先檢查 `element.is_enabled()`，
如果是 `false`，回報類似 `FAIL（元件目前不可互動，可能還在載入中或流程未到）`
而不是照樣點下去回報 PASS。

**會不會再發生**：**可能會**，只要目標元件有暫時性的 disabled 狀態（例如
資料載入中、表單未填完整前按鈕鎖住）就可能遇到，跟哪個 App 無關，屬於
`run_test_case.py` 本身邏輯還沒補齊的地方，先記錄下來之後再修。

### 24. 實測驗證：同一支 App 隔一天重掃，指紋為什麼會變

**背景**：為了測試 `viewer.html` 的「改版比對 Demo」，把 `element_map.json`
備份成 `element_map_20260818.json`（8/18掃的舊版），隔一天（8/19）重新掃描
同樣兩個畫面存回 `element_map.json`（新版），再用程式比對兩份資料的
`unique_id` 差異。`foolife_policy_overview`（保單總覽）44個元件
**完全沒有差異**，但 `foolife_health_screen`（健康吧）43→44個元件裡，
有6組元件的 `unique_id` 不一樣，逐一拆解原因如下：

**1. 動態輪播文字內容**
```
舊：「多吃蔬果及脂肪量低的肉類、非精緻澱粉等食材。」
新：「挑戰自己每日走路20分鐘，離健康就不遠了！」
```
這是畫面上一張健康建議卡片，內容本身就是**輪播/動態文案**，每次進畫面
可能顯示不同句子。`label_text` 是指紋的一部分，文字不同 → hash 直接不同。
這正是先前討論過的「動態內容元件」風險，這次是第一次抓到實例。

**2. 動態數值**
```
舊：活力分 50
新：活力分 45
```
分數本身是會變動的真實數據（跟使用者當下的健康數據連動），`label_text`
就是這個數字本身，數值一變，指紋就換了。跟第1點同一類問題，只是換成
數字型態的動態內容。

**3. 非同步資料載入時機差異**
```
舊：步數顯示「3,287」（實際數字）
新：步數顯示「-」（佔位符）
```
這個 App 的健康數據卡片是**串接 Apple Health、非同步載入**的（這個 session
掃描前也親眼看過那個轉圈圈的載入動畫）。兩次掃描剛好抓到「資料已經載入完成」
跟「資料還在載入中」兩種不同的畫面狀態，`label_text` 從真實數字變成佔位符，
指紋自然不同。**這種情況特別麻煩**：不是文案調整、不是版本改版，純粹是
「按下掃描指令那一瞬間，App 剛好處於哪個載入階段」的運氣問題，同一個版本
內重複掃描同一個畫面都可能撞到。

**4. 條件式渲染，元件整個消失**
```
舊：「差4,213步 加油」提示文字存在
新：（這段文字完全沒出現，不是id變了，是整個元件消失）
```
這是第3點連帶的後果：這段勉勵文字很可能是「有真實步數數據才顯示」的
條件式邏輯，步數變成佔位符「-」時，這段文字乾脆不渲染，導致這次掃描
連候選元件都抓不到，不是「同一個東西指紋變了」，而是「這個東西這次
根本不存在」。

**5. `sibling_index` 脆弱性的真實案例（呼應已知問題3、18）**
```
「簽到」按鈕：label_text 完全沒變，
舊：sibling_index = 28
新：sibling_index = 27
```
這組最關鍵：按鈕本身的文字、功能、位置分區都沒變，**純粹因為畫面上其他
元件的存在與否（很可能就是第4點提到、有時候會消失的那段提示文字）
讓兄弟節點的總數/順序位移了一格**，導致同一個按鈕算出完全不同的指紋。
這是先前一直用假設情境討論的「`sibling_index` 不夠精確」問題，這次終於
抓到真實資料裡的實例，證實這個弱點會實際發生，不是紙上談兵。

**6. LLM 的 `is_likely_interactive` 判斷本身不是100%穩定**
```
badge（會員等級勳章圖示）、batree_pointdge（任務值兌換圖示）：
舊版掃描時被 LLM 判斷為「不像可互動」而排除，
新版掃描時被判斷為「像可互動」而收錄
```
這是這次比對意外發現、**先前完全沒記錄過的新問題**：同樣的圖示，
兩次獨立的 LLM 呼叫（即使都設定 `temperature=0`）對「這是不是可互動元件」
給出了不一樣的判斷。LLM 本質上不是完全確定性的系統，即使溫度設到最低，
也不保證每次視覺判斷完全一致，尤其是這種本來就界於「像按鈕」和「像裝飾」
之間、比較模糊的圖示。這代表**元件地圖的完整度，本身就會因為重新掃描
而有小幅波動**，不是掃描邏輯或畫面本身的問題，是 LLM 判斷步驟自帶的
不確定性。

**這批真實資料的意義**：完整驗證了理論上討論過的三種指紋不穩定成因
（動態內容、非同步載入時機、`sibling_index`脆弱），還額外挖出一個
先前沒想到的第四種成因（LLM視覺判斷不穩定）。也證實 `foolife_policy_overview`
這種內容單純、沒有動態數據的畫面，指紋反而非常穩定（44/44完全沒差異），
代表**指紋穩定性高度取決於畫面本身有沒有動態/非同步內容**，不是所有畫面
風險都一樣高。

**會不會再發生**：**會**，只要畫面上有動態文案、即時數據、非同步載入
的內容，幾乎每次重新掃描都可能遇到類似情況，這也是 PROJECT_BRIEF
決策3（改版相似度比對）存在的根本原因——單純用「hash是否完全相同」
判斷「是否為同一元件」，在這種真實場景下完全不夠用。

### 25. 新增：掃描前輪詢畫面穩定，緩解非同步載入造成的不穩定（問題24第3、4點的部分解法）

**背景**：問題24發現的4種指紋不穩定成因裡，「非同步資料載入時機差異」
（第3點：步數顯示 `3,287` vs 佔位符 `-`）跟「條件式渲染導致元件消失」
（第4點）這兩種，本質上是**暫時性**的——只要多等一下讓資料載入完成，
內容就會定下來，不像動態文案/數值（第1、2點）或輪播 banner 那樣是
設計上就會持續變動、永遠不會有「穩定」的一刻。這兩種問題的成因不同，
需要用不同方式處理，不能混為一談。

**解法**：`capture_screen_map.py` 新增 `wait_for_screen_stable()`，
在正式掃描（含裁切截圖、呼叫LLM生成描述）之前，先反覆讀取 `page_source`
解析候選元件、算出一個簽章（`class`+`native_id`或`label`+`position_bucket`
的集合），連續兩次讀到的簽章一致才判定「畫面已穩定」，最多輪詢5次
（間隔1.5秒），超過還沒穩定就印出警告、承認需要人工複核，但仍照最後
一次讀到的內容繼續往下產出結果（不會卡住整個流程）。這個檢查只重複讀
Tree，不呼叫LLM、不截圖，成本很低。

畫面資料新增 `screen_stable_at_scan` 欄位（`true`/`false`），記錄這次
掃描當下有沒有通過穩定性檢查，之後校對資料時可以優先複核標記 `false`
的畫面。

**實測結果**：在保單總覽頁（無動態內容）測試，1次輪詢後2次讀取內容
就一致，只多花約1.5秒；刻意在健康吧頁面還在轉圈圈載入中的當下觸發掃描，
也是2次讀取後就判定穩定，正確等到資料載入完成才繼續往下掃描，沒有像
先前那樣抓到佔位符內容。

**這個機制解決不了什麼**：對問題24第1、2點（動態文案、動態數值）跟
輪播 banner 完全沒有效果——這些內容不是「還沒載入完」，是「本來就會一直
不一樣」，輪詢到上限一樣會判定不穩定，這是**預期行為**，代表這類內容
需要靠 PROJECT_BRIEF 決策3的相似度比對去容忍，不是掃描時機的問題，
兩者需要的解法完全不同（見問題24的完整討論）。

**會不會再發生**：這是主動預防機制，正確運作的話問題24的第3、4點
會大幅減少，但沒辦法保證100%不發生（例如載入時間剛好超過5次輪詢的
上限）。輪詢次數/間隔目前是寫死的（5次、1.5秒），如果之後遇到載入
特別慢的畫面，可能需要依情況調整這兩個參數。

### 26. Android版：同一個 resource-id 被多個不同元件共用，unique_id 跟 LLM 描述互相覆蓋

**背景**：Android 版（`capture_screen_map_android.py`）第一次對你好證券
「我的」分頁（未登入狀態）掃描成功後，人工核對輸出資料時發現：「股票抽籤」
「額度調整」「教學懶人包」「期貨開戶」「研究報告」「股票出借」這6個明顯不同
的按鈕，`native_id` 全部都是 `com.foo.eservice:id/btnFavorite`，
且全部拿到一模一樣、內容也對不上的 LLM 描述：「點擊進入『申辦投信帳單』
功能按鈕」。

**現象**：39個候選元件當時全部被判定為 native（39 native / 0 generated），
但其中這6個顯然是不同功能的按鈕，卻共用同一個 `class::native_id` 組合。

**原因**：這是 Android 特有、iOS 上沒遇過的情況。iOS 的
`accessibilityIdentifier`（`name`）通常是開發者針對「這一個」元件手動設定的；
但 Android 的 `resource-id` 常常是**版型內部元件的 id**，在
RecyclerView/ListView/GridView 這類清單畫面上，每一列/每一格用的是同一份
版型（layout XML），版型裡的「收藏按鈕」不管套到哪一列，`resource-id`
都叫 `btnFavorite`——這是 Android 開發的正常/預期寫法，不是這支 App 寫得不好。

連鎖影響兩個地方：
1. `make_native_unique_id(screen_name, class, native_id)` 對這6個按鈕算出
   完全相同的 `unique_id`，違反「每個元件一個可長期追蹤的唯一ID」的設計前提
   （比已知問題13更嚴重——問題13是「同一 native_id 出現在不同 class」，
   這次是**同一個 class + 同一個 native_id 出現在多個不同元件上**，
   問題13的解法對這個情況完全沒用）
2. `describe_native_elements()` 用 `f"{class}::{native_id}"` 當查找表的 key，
   6個按鈕全部撞成同一個 key，LLM 針對6個不同輸入各自生成的描述，
   在組成字典時後面的結果會直接覆蓋前面的，最終6個按鈕全部拿到
   同一個（且是最後一筆的）描述

**解法**：`parse_candidate_elements()` 新增第二輪統計：解析完所有候選元件後，
統計同一個畫面上每個 `(class, resource_id)` 組合各出現幾次。出現超過1次的，
一律把該元件的 `native_id` 降級成 `None`（等同於「視為沒有 native id」），
改走原本給無 id 元件用的 fingerprint 路徑（`label`/`position_bucket`/
`sibling_index`/`nearby_text` 組 hash），並印出警告列出被降級的
resource-id 清單。`resource-id` 原始值不會丟失，只是不再拿來當
`unique_id`/描述查找的依據。

**實測結果**：同一批資料重新掃描，`btnFavorite` 被正確偵測並降級，
結果從「39 native / 0 generated」變成「21 native / 18 generated」，
原本6個撞在一起的按鈕各自拿到獨立的 `unique_id`，且描述也各自對應正確
（「股票抽籤」→股票抽籤功能、「期貨開戶」→期貨線上開戶，皆正確對應）。

**會不會再發生**：**會**，只要是清單/網格類版面（Android 很常見的
RecyclerView 模式），幾乎一定會遇到同一個 resource-id 被多個項目共用的情況；
但現在已經有自動偵測+降級機制擋下，不會再產生碰撞。這也代表 Android 版的
「native id 涵蓋率天生比iOS高」這個原始假設要修正：**resource-id「存在」
的涵蓋率確實比較高，但「存在」不等於「在這個畫面上唯一」**，兩者是不同的
屬性，Android 版必須額外驗證後者，iOS 版目前不需要（尚未實測到 iOS 有
同樣的重複 accessibilityIdentifier 情況，如果之後遇到，可以比照這裡的做法
加同樣的統計降級邏輯）。

### 27. Android版：畫面校驗抓不出「捲動位置不對」，只要頭尾固定元件都在就誤判 100% 吻合（尚未修正）

**背景**：驗證「畫面下滑後才看得到的元件，掃描抓不抓得到、測案能不能執行」時，
先在你好證券「我的」分頁往下滑一次再重新掃描（存成
`foo_android_my_screen_scrolled`），比對滑動前後的元件清單，證實
Android 的 Accessibility Tree **只反映當下實際渲染出來的內容**：滑動後
多出「個資變更」「功能管理」「我的點數」「電子帳單」4個原本抓不到的元件，
同時「立即登入」「嗨，你好」這些滑出畫面上方的元件從清單裡消失。這點
跟 iOS（已知問題16：捲動清單裡的元件即使沒顯示，Tree 一樣抓得到座標）
行為不同，是這次才確認的平台差異。

**先確認測案執行本身是安全的**：手機保持在滑動後的位置執行測案，針對
這4個新元件做 `assert_visible`，4/4 PASS（XPath 用 `text`/`content-desc`
正確定位）；接著故意把手機滑回頂部（模擬「畫面校驗通過了、但其實內容
不是掃描當下那個捲動位置」的情境）再執行同一個測案，4個步驟全部正確
回報 `SKIP（無 native id 且 XPath 查無唯一結果...）`，沒有誤判成功、
也沒有誤觸座標點擊——這部分行為符合預期，沒有問題。

**問題出在畫面校驗本身**：把手機滑回頂部後，`verify_current_screen()`
依然回報「17個native元件中，目前畫面找到17個（100%）」，完全沒有發現
其實已經不是掃描當下的捲動位置。原因是這個畫面的 native 元件清單
（`tvMiddle`「我的」標題、`tvQuotation`「行情」/`tvFilter`「選股」/
`tvOrder`「下單」/`tvBill`「帳務」/`tvMy`「我的」底部導覽列圖示等）
**全部都是不受捲動影響、固定貼在頂部/底部的介面元件**，完全不在可捲動
的內容區域（`ScrollView` 範圍 `[0,262]`~`[1080,2206]`）裡。`verify_current_screen()`
的設計是「抽查已知 native 元件，過半數找得到就當作畫面吻合」，但當一個
畫面剛好符合「native 元件都是頭尾固定列、真正的內容都是 generated（指紋）
元件」這種常見版面模式時，這個抽查機制會對「捲動位置不對」完全視而不見。

**這會造成什麼實際影響**：如果一個測案前幾步剛好是操作頭尾固定的
native 元件（例如先 `assert_visible` 標題），後面接的步驟才是操作
捲動內容裡的 generated 元件，執行時畫面校驗會顯示「通過、100%吻合」，
但後面的步驟卻默默 `SKIP`——測試報告乍看之下會讓人以為「畫面明明校驗
過了，為什麼後面沒執行」，不會直覺聯想到其實是捲動位置沒對齊，
增加排查的困難度。

**尚未修正，可能的解法方向（先記錄，未實作）**：
1. `verify_current_screen()` 抽查對象不要只看 native 元件，也把該畫面
   已知的 generated 元件（用 XPath）一併納入比對，會比純看 native 更能
   反映「捲動內容區域」的實際狀態
2. 掃描階段記錄「這個畫面是否有可捲動容器」，畫面校驗時如果偵測到
   有 `scrollable="true"` 的容器，額外提示「這個畫面存在捲動內容，
   校驗結果可能無法完全反映內容區域的捲動位置，建議人工確認」
3. 更直接的做法：執行測案前，先用測案裡第一個 generated 元件所在的
   `position_bucket`/`sibling_index` 資訊，判斷需不需要先自動捲動到
   對應位置，而不是假設手機已經在正確的捲動位置上
4. **（Android專屬，理論上最權威的解法）** Android 每個畫面在系統層級
   就是一個 Activity，Appium 可以直接用 `driver.current_activity` 問
   系統「目前前景是哪個 Activity」——這是作業系統直接回答的事實，不是
   像現有做法靠元件存在率去推論，完全不受捲動位置/畫面內容變化影響。
   掃描時把 Activity 名稱一併存進 `element_map.json`，執行測案前先比對
   `current_activity` 是否相符，可以在 Android 上從根本解決本問題（不用
   再猜，直接問系統），現有的元件比對可以留著當補充。
   **iOS 沒有對應的東西可用**：iOS 的畫面單位是 ViewController，但這是
   App 內部程式結構，不像 Android 的 Activity 是系統元件，XCUITest/
   Appium 沒有提供「目前是哪個 ViewController」的查詢管道，iOS 只能
   繼續依賴元件層級的推論，沒有更權威的替代方案。
   （討論於此，使用者確認先記錄、不實作）

**會不會再發生**：**會**，只要 Android 畫面符合「native 元件集中在
頭尾固定列、真正要測的內容在可捲動區域裡」這種常見版面模式（例如這次
的你好證券「我的」分頁，或任何有底部導覽列+可捲動內容的畫面），就會
複現同樣的校驗盲區。目前 generated 元件本身的定位邏輯是安全的（查不到
就老實 SKIP，不會誤判/誤點），風險僅限於「畫面校驗這道防線失靈，
排查測試報告時容易誤判原因」，不是會誤觸真實操作的等級，但仍建議
之後找時間補上述解法之一。

### 28. 捲動內容裡的元件，執行測案時原本的定位方式會失敗（已修正）

**背景**：問題27發現「畫面校驗抓不出捲動位置不對」之後，接著追問一個更根本
的問題：如果測案的目標元件本身就在捲動內容裡，而手機執行測案當下沒有先
捲到對應位置，這個元件到底還能不能被正確定位、點擊/驗證？

**現象**：實測把手機捲回頂部（模擬「畫面校驗誤判通過，但捲動位置其實不對」
的情境），對「個資變更」等4個只在捲動內容裡才存在的元件執行 `assert_visible`，
原本的 XPath 定位（`_locate_by_xpath`，查 `@text`/`@content-desc`）全部查到
0個結果，只能回報 `SKIP`——這部分行為本身是安全的（不會誤判成功、也不會
誤觸座標），但代表**只要手機沒有先手動捲到正確位置，捲動內容裡的元件在
測案中完全無法被操作**，達不到「完整地圖」該有的可用性。

**原因（Android／iOS 根本成因不同，這次一併查證清楚）**：
- **Android**：畫面外（沒捲到）的元件，很多情況下**節點根本沒有被建出來**
  （直接查證過原始 XML 全文，目標文字完全不存在，不是被過濾掉），所以
  XPath 查詢的對象根本不存在，不管怎麼查都是0個結果，這跟網頁的 DOM
  不一樣——網頁元件即使被捲出畫面外，DOM 節點仍完整存在於記憶體裡，
  XPath 查得到；Android 這種常見的懶載入/view recycling 機制導致這個
  假設不成立。
- **iOS**：情況相反，元件即使捲出可視範圍外，Accessibility Tree 依然
  找得到（節點真的存在，跟已知問題16的發現一致），但**找到不代表能點**
  ——不在可視範圍內時直接呼叫 `.click()`，在 XCTest 底層等同無效觸控，
  原本的 `run_tap()`/`run_assert_visible()` 完全沒有檢查這件事。

**解法（兩邊用不同 API，因為卡住的環節不同）**：
- **Android**（`run_test_case_android.py`）：新增 `_locate_by_scroll_into_view()`，
  XPath 查不到時，改用 UiAutomator 原生的
  `UiScrollable(new UiSelector().scrollable(true)).scrollIntoView(new UiSelector().text(...))`
  （或 `.description(...)`）——這是 Google 官方測試框架處理「元件在可捲動
  容器裡、目前捲動位置不對」的標準做法，把「捲動」跟「尋找」合成一個指令，
  自動捲動已知的可捲動容器、邊捲邊找，不用自己算捲動距離。
- **iOS**（`run_test_case.py`）：新增 `ensure_visible()`，找到元件後、實際
  點擊/驗證前，先檢查 `visible` 屬性，不是 `true` 才呼叫
  `driver.execute_script("mobile: scroll", {"element": element.id, "toVisible": True})`
  捲到可互動範圍，才繼續。

**實測結果**：手機刻意捲回頂部後重跑同一個測案，4個步驟全部從 `SKIP`
變成 `PASS（XPath / UiScrollable 定位）`——第一個元件因為 XPath 查不到
觸發了 `UiScrollable.scrollIntoView`，捲動後順帶把後面3個元件也帶入畫面，
剩下3步驟直接用 XPath 就命中，不用再觸發一次捲動。

**這個修正如何影響問題27**：問題27（畫面校驗誤判100%吻合）本身還沒修，
但這次修正讓它的實際風險降低——即使畫面校驗誤判通過、手機當下捲動位置
跟掃描時不同，後續步驟現在會**自動捲到正確位置再操作**，不會再默默
`SKIP`。校驗本身的盲區還在，只是後果沒有原本想的那麼嚴重了。

**會不會再發生**：這個修正對任何有捲動內容的畫面都適用，不限這支 App，
但要留意 `UiScrollable.scrollIntoView` 只認得到 `scrollable="true"`
那一層容器，如果畫面有巢狀捲動區域，可能會抓錯層或找不到，屬於已知的
Android 官方 API 本身限制，不是我們程式碼的問題。

### 29. Android版：`is_likely_interactive` 判斷誤把「一律收錄」的文字元件排除（已修正）

**背景**：另開一個 session 建了一支專門用來測試自動化工具的靶場 App
（`com.testfield.bankapp`，規格見 `ANDROID_TEST_APP_SPEC.md`），首頁掃描完後
人工核對發現：畫面上明明有一個「推薦專區（左右滑動）」的橫向捲動卡片區塊
（3張卡片，各有標題+副標題文字），但 `element_map.json` 裡完全沒有這幾筆資料。

**現象**：掃描時有印出「偵測到 resource-id 在同畫面重複使用...
`tv_card_title`、`tv_card_subtitle`」（問題26的機制正確觸發，判斷這些卡片
標題共用 resource-id、正確降級成 generated 元件），但最終「找到候選元件數量31」
只產出22筆結果，少了9筆，卡片標題/副標題就在這消失的9筆裡。

**原因**：`capture_screen_map_android.py` 的 `ALWAYS_KEEP_CLASSES = {TextView,
EditText}` 設計本意是「不管可不可點擊都要收錄」（斷言/驗證文字內容用），
用來跳過原本只收 `clickable/checkable` 的篩選。但 `scan_screen()` 裡，所有
generated 元件（不論原本是因為「可能可點擊」還是因為「ALWAYS_KEEP_CLASSES
一律收錄」才進候選清單）**沒有區分來源，一律送去問 LLM 同一個問題**：
「這個東西看起來像不像可以點擊」（`is_likely_interactive`），答案是 `false`
就整筆排除。卡片標題純粹是顯示用文字，LLM 判斷「不像可互動」完全正確——
但這個判斷本來就不該套用在 `ALWAYS_KEEP_CLASSES` 收錄的元件上，等於
`ALWAYS_KEEP_CLASSES`「一律收錄」的設計形同虛設。

這個問題其實是從 iOS 版沿用邏輯時就存在的根本性設計問題，只是這次才第一次
被抓到：iOS 版的 `is_likely_interactive`（問題15）是為了彌補「`Image` class
用猜的、不知道是不是裝飾用途」這個弱點才存在，但 Android 版的候選判斷
（`clickable`/`checkable` 屬性）本身就是系統直接回報、可靠的訊號，不像
iOS 需要用 class 白名單去猜——**Android 版把 iOS 這套「為了彌補猜測誤差」
的機制原封不動複製過來，套用在根本不需要猜的情況上，反而製造了新問題**。

**解法**：討論後決定簡化，不是修補「排除規則」，而是直接把 `is_likely_interactive`
判斷從 Android 版整個拿掉——`describe_generated_elements()` 只生成
description，不再判斷要不要收錄；`scan_screen()` 也拿掉對應的過濾迴圈。
有截圖／無截圖（FLAG_SECURE）兩條路徑統一成「都只生成描述、都全部收錄」，
不用再分支處理，程式碼也更簡單。**這個簡化只套用在 Android 版，iOS 版的
`is_likely_interactive` 保留不動**——因為 iOS 的 `Image` class 是粗篩、猜測
範圍廣（背景圖、大張插圖、Logo都會先進候選清單），拿掉判斷會讓大量純裝飾
圖片流入元件地圖，雜訊變多，跟 Android 的情況不對稱，不能套用同一套結論。

**實測結果**：同一個首頁重新掃描，候選元件31個、輸出31筆，數量一致，
不再遺漏；卡片標題「推薦 1」「推薦 2」「推薦 3」與副標題「點我看看」全部
正確收錄，描述內容也正確對應。

**會不會再發生**：這類問題不會再發生在 Android 版（判斷邏輯已整個移除）。
但這次的教訓值得記住：**跨平台移植邏輯時，原邏輯存在的理由要跟著一起搬過去
確認是否還成立，不能只搬「怎麼做」，沒搬「為什麼這樣做」**——這正是這次
問題的根源。

### 30. 架構調整：掃描端不再過濾，全部收錄，篩選交給 viewer.html（兩平台，設計決策非bug）

**背景**：問題26（Android resource-id共用被誤判）跟問題29（`is_likely_interactive`
誤把該收錄的TextView排除）兩次都是同一種模式：**掃描階段就先幫使用者
決定「這個元件值不值得收錄」，決定錯了就是真實資料憑空消失**，而且要
等人工核對才會發現。討論後決定從根本調整這個設計：掃描端只負責「忠實
記錄畫面上有什麼」，「要看哪些」的決定權整個移交給檢視工具。

**改動內容**：
- **Android**（`capture_screen_map_android.py`）：拿掉 `is_candidate()`
  跟 `ALWAYS_KEEP_CLASSES`（原本只收 `clickable`/`checkable` 或
  TextView/EditText）。現在只要節點有 `class` 屬性、`displayed != false`、
  座標可解析，一律收錄，不再管是不是clickable、是什麼class
- **iOS**（`capture_screen_map.py`）：拿掉 `INTERACTIVE_CLASSES` 白名單
  （原本只收 Button/TextField/Cell/Image等特定class）。現在只要節點
  `visible=true`、座標可解析，一律收錄
- **兩邊都拿掉 `is_likely_interactive` 判斷**（iOS版原本因為Image class
  猜測範圍廣而保留，這次一併拿掉，因為篩選責任已經整個移到viewer端，
  掃描階段沒有必要再做這層猜測）
- **原始屬性照實記錄，不再用來篩選**：Android新增 `clickable`/`checkable`/
  `enabled` 三個布林欄位；iOS新增 `enabled`/`accessible` 兩個布林欄位，
  都存進每個元件的JSON資料裡
- `viewer.html`「元件校對」分頁新增篩選列：
  - id來源（native/generated）checkbox
  - class 多選（依上傳資料當下實際出現過的class動態產生選項與筆數，
    不寫死清單，換一支App/換平台也能用）
  - 原始屬性（依資料裡實際存在的布林欄位動態產生下拉選單，例如iOS資料
    沒有clickable欄位就不會顯示clickable篩選）
  - 篩選會同步套用在左側元件清單跟右側截圖疊框，可以跟既有的關鍵字
    搜尋疊加使用，「重設篩選」一鍵清空

**唯一保留的排除條件（技術限制，不是篩選意見）**：節點沒有`class`屬性
（Android的`<hierarchy>`根節點本身）、`displayed`/`visible`為false（技術上
真的沒有東西被畫出來，無法疊框/裁切）、座標無法解析。這幾項不算「篩選」，
是「這個元件根本沒有可用資料可以記錄」的技術性排除。

**代價（已知、刻意接受的取捨）**：候選元件數量會明顯增加——Android測試App
首頁從31筆變成60筆（多了LinearLayout/FrameLayout這類純版面容器）；iOS
因為畫面階層通常比Android更深、容器節點更多，增幅可能更明顯。連帶影響：
LLM描述批次呼叫的payload會變大（但因為還是批次呼叫、不是逐元件呼叫，
API請求次數不會增加，只是單次請求內容變多），元件地圖檔案本身也會變大。

**實測結果**：`testapp_home` 重掃後60個候選元件，`clickable`/`checkable`/
`enabled`欄位正確寫入；`viewer.html`實際用瀏覽器操作驗證，篩選介面正確
依資料動態產生選項，篩 `clickable=true` 從60筆正確縮到15筆，重設篩選、
搜尋疊加篩選都正常運作，console無錯誤。

**會不會再發生**：這是刻意的設計調整，不是意外發生的問題。之後如果
覺得「全部收錄」造成雜訊太多、LLM成本太高，可以考慮的方向：viewer.html
篩選介面上再加「隱藏純版面容器（無文字、不可互動、沒有子元件文字）」
這類複合篩選條件，或是在掃描端針對LLM描述生成這一步做量的節流（但
「收不收錄進JSON」跟「值不值得取得LLM描述」可以是兩個獨立的決定，
不用綁在一起處理）。

### 31. 新功能：「邊捲邊抓」自動收集捲動內容（兩平台）

**背景**：問題27/28發現「捲動位置不對」會讓畫面校驗誤判、也會讓元件找不到，
根本原因是掃描本來就「只抓當下畫面渲染出來的內容」，捲動內容裡沒顯示的
元件抓不到。之前的解法是手動捲動、分開存成不同 `screen_name`，這次改成
掃描時自動偵測、自動收集完整清單。

**設計**：
1. 掃描時先檢查畫面有沒有可捲動容器（Android看 `scrollable="true"` 屬性；
   iOS看有沒有 `ScrollView`/`Table`/`CollectionView` 類型的節點）
2. 有的話，反覆執行「讀取候選元件 → 判斷還能不能繼續捲 → 往下捲一段」，
   把每一輪抓到的元件依內容識別（不看捲動位置，因為同一個元件在不同輪次
   的螢幕座標本來就不一樣）去重合併
3. 收集完後自動捲回頂部，不影響後續操作
4. 每個元件記錄自己是哪一輪抓到的（內部欄位，不寫進最終JSON），生成LLM
   描述、裁切截圖時使用「那一輪」的截圖，不會用錯畫面內容去描述元件

**先確認過一個更簡化的做法為什麼行不通**：曾經討論過「乾脆一次捲到底、
只抓最後一次就好」，但已經有實測證據證明不行——你好證券「我的」分頁
捲到底後重掃，捲動前的「立即登入」等元件直接從 Tree 上消失（不是被過濾，
查證過原始XML完全不存在），因為 Android 的清單容器（尤其RecyclerView）
會回收畫面外的項目。這代表**只能邊捲邊抓、每一段都要停下來記錄**，不能
偷懶只抓最終位置。

**實測結果（Android，`testapp_list` 長清單畫面，85個「項目 001~085」+對應
刪除按鈕）**：13輪收集，185個候選元件，全部 `unique_id` 不重複，85筆
項目標題完整涵蓋001到085無缺漏。iOS 依照同樣設計實作，但這次沒有接手機，
沒有實測驗證，這是已知的落差，之後有裝置時需要補測。

**會不會再發生**：這是新增的核心功能，之後任何有捲動內容的畫面都會自動
套用，不需要再手動處理（除了問題34提到的橫向捲動限制）。

### 32. 「邊捲邊抓」合併去重誤判：只看 native_id 會把不同元件錯誤合併成一筆（已修正）

**現象**：問題31剛做出來、第一次實測 `testapp_list`（85個「項目001~085」
標題文字，全部共用同一個 resource-id `tv_item_title`）時，合併結果**只剩
1筆標題**，而且被誤判成 native（應該要跟問題26一樣被降級成generated）。

**原因**：合併去重用的識別 key（`candidate_identity_key`）當時邏輯是「有
native_id 就用 `(class, native_id)` 當key」，這個假設在「邊捲邊抓」的情境
下不成立——這個階段的 native_id 都還沒經過同畫面重複檢查（Android的
`downgrade_duplicate_native_ids()` 要等所有輪次合併完才會執行一次），
如果同一個 resource-id 本來就被畫面上多個不同項目共用（清單版型常見，
問題26的情境），85個不同標題的 key 會全部一樣，被誤判成「同一個元件在
不同輪次重複出現」，錯誤合併成1筆。

**解法**：合併 key 加入 `label`——`(class, native_id, label)`。這樣同一個
resource-id但文字不同的項目會拿到不同key，不會互相吃掉；同一個元件在
重疊輪次裡重複出現時，label通常不變，還是能正確合併去重。iOS版雖然還沒
實測到這個問題，但同樣的防呆邏輯也一併加上去了。

**實測結果**：修正後重跑 `testapp_list`，85筆「項目001~085」標題完整無缺，
全部 `unique_id` 不重複。

**會不會再發生**：不會（邏輯已修正），但這是個值得記住的教訓：**跨畫面/
跨輪次的「這是不是同一個元件」判斷，永遠不能只信任單一屬性（尤其是還沒
驗證過唯一性的 native_id），這正是問題26一開始會發生的同一個根本原因，
這次在合併邏輯裡又重蹈覆轍了一次**。

### 33. Android版捲動手勢沒有檢查回傳值，導致捲不動時無法正確停止（已修正）

**現象**：問題32修好、重測 `testapp_list_full` 時，程式執行超過10分鐘沒有
反應，用 `lsof` 檢查發現卡在跟 Appium server（本機4723埠）的一個請求上，
不是在等LLM API。查看 Appium log 發現：`mobile: scrollGesture` 連續兩次
往下捲都回傳 `value: false`，但程式完全沒有檢查這個回傳值，繼續照原訂
流程跑，最後卡在收集完後「捲回頂部」那一步——原本用一個 `percent=12`
（捲動區域高度的12倍）的超大單次手勢想一次捲回頂部，這個異常大的數值
讓 UiAutomator2 執行得極度緩慢甚至疑似卡住。

**原因**：兩個問題疊加。第一，原本判斷「該不該停止收集」的邏輯是比對
「連續兩輪內容是否完全一樣」，沒有用上 `mobile: scrollGesture` 這個指令
本身就會回傳的布林值（這個回傳值直接代表「這次手勢有沒有讓畫面真的移動」，
是系統層級的權威判斷，之前設計時沒注意到這個API有這個能力，見討論中對
「怎麼確保有捲到全部內容」的分析）。第二，「捲回頂部」的清理步驟為了省事
用了一個超大 `percent` 值一次捲完，沒有像收集階段那樣用同樣大小、多次
執行的方式。

**解法**：
1. 新增 `scroll_step()`，直接讀取 `mobile: scrollGesture` 的回傳值當作
   「還能不能繼續捲」的判斷依據，取代原本的內容比對邏輯——這個回傳值
   不會被「單一超大元件讓內容看起來沒變」騙到（這是討論設計時就提出的
   疑慮），也不會有「動畫元素讓比對誤判成還在變化」的問題，比內容比對
   更直接可靠
2. 「捲回頂部」的清理步驟改成跟收集階段同樣大小的手勢，用迴圈重複執行
   直到系統回報捲不動為止，不再用單次超大幅度的手勢

**實測結果**：修正後重跑，13輪正確收集185個元件，在系統回報「已經無法
再往下捲」時乾淨停止，沒有再卡住。

**會不會再發生**：不會（已改用更可靠的判斷依據）。這也連帶回答了之前
討論「如果元件超過整個畫面、固定百分比捲動會不會漏東西」的疑慮——
答案是「用回傳值判斷就不會有這個風險」，Android版現在用的正是這個做法。

**iOS版的已知落差**：`mobile: scroll` 沒有找到對應的權威回傳值可用，
iOS版目前還是用「連續兩輪內容比對」當停止依據，前述的「超大元件」風險
在 iOS 版上依然存在，尚未解決，屬於已知的兩平台可靠度落差。

### 35. fingerprint 不記錄捲動位置的兩個殘留風險（已知，尚未修正）

**背景**：問題31上線「邊捲邊抓」之後，追問「fingerprint 有沒有記錄捲動
百分比，沒有的話自動化測試怎麼點得到」，釐清設計上**不需要**記錄——執行
測案時的定位（Android用 `UiScrollable.scrollIntoView()`、iOS用
`mobile: scroll toVisible`，見問題28）是靠內容比對「邊捲邊找」，本來就
不依賴掃描當時記錄的捲動位置。但討論過程中發現兩個尚未處理的殘留風險，
記錄下來：

**風險1：label 為空的元件，座標備援可能點錯位置**

`locate_generated_element()` 需要 `label`（文字內容）才能組出 XPath/
UiSelector 查詢。如果元件沒有文字也沒有 content-desc（純圖示按鈕這類），
`label` 是空字串，程式會直接跳過 XPath 跟 `scrollIntoView`，退回座標點擊
——用的座標是「這個元件被抓到那一輪」在螢幕上的座標，如果執行測案時手機
的捲動位置跟那時候不一樣，這組座標就是錯的，會點到不相關的內容。這是
舊有風險（問題22/27類：座標備援在畫面狀態對不上時可能誤觸）在「捲動
內容」情境下的延伸，目前沒有額外防護。

**風險2：改版比對可能因為捲動輪次不同而變得不穩定**

`fingerprint` 裡的 `position_bucket` 記的是「這個元件被抓到那一輪，在
螢幕上的九宮格位置」，不是一個跟捲動狀態無關的固定值。同一支 App 沒有
真的改版，只是兩次掃描剛好在不同輪次捲到同一個元件（例如兩次捲動速度、
輪詢時機有些微差異），`position_bucket` 就可能不一樣，讓
`compare_versions.py` 的相似度分數多一個不必要的雜訊來源，可能把「其實
沒變的元件」誤判成 `needs_review` 甚至 `new`。這是「邊捲邊抓」上線後才
浮現的新副作用，目前還沒有實際觀察到發生（需要拿同一個有捲動內容的畫面
隔一段時間重掃兩次來驗證），先記錄下來。

**尚未修正，兩者都還沒有具體解法**：風險1可能的方向是幫這類元件也想辦法
取得一個穩定識別線索（例如改用它在容器裡的相對順序而非螢幕座標）；風險2
可能的方向是計算相似度時降低 `position_bucket` 的權重、或排除捲動內容
元件的這個維度，兩者都還沒設計，只是先點出問題。

**會不會再發生**：風險1只要遇到捲動內容裡的純圖示元件就可能發生；風險2
需要對同一個捲動畫面做多次改版比對才會顯現，目前使用量還不足以判斷實際
發生機率。

### 36. 清單裡文字相同的操作按鈕，定位會默默選錯（已修正）

**背景**：用剛做好的「viewer.html 即時操作模擬器」功能實測 `testapp_list`
長清單畫面時，使用者回報「點擊按鈕好像點不準，點不到真的那一個」。

**現象**：查證發現，`testapp_list` 清單裡每一列都有一個文字固定是「刪除」
的按鈕（85列，全部文字一模一樣），實際查詢畫面上同時符合
`class=Button, text="刪除"` 的元件，一次就有 **11 個**（RecyclerView 當下
渲染出來的可視範圍內）。

**原因**：`_locate_by_xpath()` 查詢符合條件的元件數量不等於1時會正確判定
「有歧義」而放棄（回傳None，這部分是安全的），但退回的備援
`_locate_by_scroll_into_view()` 用的 UiSelector 查詢條件是**同一組**
class+文字，`find_element`（單數）在有多個符合的情況下**不會報錯，
會默默回傳第一個找到的**——不保證是使用者要操作的那一個。這代表原本
選定「項目 003」那一列的刪除按鈕，實際執行時可能點到「項目 001」
或任何一個當下畫面上找得到的「刪除」按鈕，卻還是回報 PASS，是個
**不會報錯、看起來成功、但操作到錯誤目標**的隱藏風險，比明確的
FAIL/SKIP更危險。

**解法**：新增 `_locate_by_anchor()`，改用 fingerprint 裡本來就有記錄
的 `nearby_text`（同一列裡能唯一辨識這一列的文字，例如「項目 003」，
掃描時 `parse_candidates_raw()` 就已經算出來，只是原本沒有拿來定位用）
當錨點消歧義：
1. 用 `UiScrollable.scrollIntoView()` 把錨點文字（通常才是真正唯一的）
   捲到畫面上，同時解決「元件還沒捲到畫面內」的問題
2. 取得錨點的 Y 座標
3. 在所有符合目標 class+文字 的候選裡，挑 Y 座標離錨點最近的一個
   （同一列的元件彼此 Y 座標通常很接近）

定位順序更新為：XPath（唯一才用）→ 鄰近文字錨點消歧義 → 純
`UiScrollable.scrollIntoView`（沒有 nearby_text 可用時的次佳備援，
在文字不唯一時可能還是會選錯，只是沒有更好選項時的保底）→ 座標點擊。

`viewer.html` 的「目前定位方式」顯示也一併更新：偵測到 `nearby_text`
存在時，會在 XPath 字串後面加註「若同文字元件不只一個，會改用鄰近文字
『項目 003』定位同一列」，讓使用者知道實際執行時不是只看那條 XPath。

**實測結果**：用 Python 直接測試 `testapp_list_full::gen::a5238028`（「項目
003」的刪除按鈕），log 印出「用鄰近文字『項目 003』（y=618）從 11 個
同文字候選中挑出最接近的一個」，定位到的元件 y=584，跟同畫面上「項目
003」標題文字（y=618）只差 34px，確認是正確的那一列；再透過瀏覽器
「驗證可見」按鈕完整走過一次 browser→server→Appium 全流程，回報 PASS。

**會不會再發生**：這個問題只要是清單裡「每一列都有一個文字相同的操作
按鈕」（刪除、編輯、查看明細、加入最愛等) 這種常見版型都會遇到，不限
這支測試App。已修正，只要該元件的 `nearby_text` 有記錄到能唯一辨識
所在列的文字就能正確消歧義；如果 `nearby_text` 本身也不唯一（例如同一
畫面有兩列標題剛好文字一樣），這個機制目前沒有更進一步的備援，會退回
次佳的 `scrollIntoView`，理論上還是有選錯的風險，屬於已知殘留限制。

### 37. 新功能：「重新定義 XPath」（第一次掃描定位不準時的人工救援機制）

**背景**：問題36修好之後，接著討論到一個更根本的問題：如果自動推導的定位
方式（native id / XPath / 錨點消歧義 / scrollIntoView）全部都不準確，
有沒有辦法讓使用者自己動手定義？答案是可行，設計如下：

**架構**：
1. `viewer_server.py` 新增兩個輔助 API：
   - `/inspect`：先用現成的定位鏈（`_locate_best_effort`，沿用
     `locate_generated_element` 全部邏輯）盡力找出這個元件目前對應的畫面
     位置，取得即時座標，再解析當下完整 tree、往上層走訪，回傳每一層
     容器的 class/resource-id/文字，供使用者參考
   - `/test_xpath`：讓使用者在儲存前先測試自己寫（或系統建議）的 XPath
     查到幾個結果，不用真的存檔、真的執行測案才知道查詢對不對
2. `viewer.html` 每個 Android 元件卡片新增「✏️ 重新定義」按鈕，展開後有：
   可編輯的 XPath 輸入框（預填目前自動推導出的查詢，注意要用純 XPath
   字串，不能混入畫面顯示用的中文提示文字）、「載入上層元素」下拉選單
   （選了會自動帶入建議查詢模板）、「測試查詢」即時回報命中數、
   「儲存」/「清除自訂」
3. `run_test_case_android.py` 新增 `_locate_by_custom_xpath()`，在
   `run_tap()`/`run_assert_visible()` 最前面優先檢查
   `el["custom_xpath"]`——人工測試過確認「查到唯一一個」才存的查詢，
   比自動邏輯更值得信任，優先使用

**實測結果**：對 `testapp_list_full::gen::a5238028`（「項目 003」的刪除
按鈕，問題36的同一個元件）完整走過一次：載入8層上層元素 → 選第1層
（LinearLayout）→ 自動帶入建議查詢 → 測試查到1個（唯一）→ 儲存 → 
「驗證可見」按鈕正確回報「PASS（人工自訂XPath定位）」，確認優先序生效。

**開發過程中額外發現並修正兩個真實bug，見問題38、39**——都是靠這次
end-to-end實測才抓到，不是設計階段就想到的。

**會不會再發生**：這是新增功能，不是bug。之後遇到自動推導的定位方式都
不準確、又不想改動掃描邏輯的情況，都可以用這個機制人工介入。

### 38. 「重新定義XPath」建議查詢模板語法錯誤：範圍沒有真的縮小到指定的那一層（已修正）

**現象**：實測時，選擇「第1層 LinearLayout」（刪除按鈕的直接父容器）套用
建議查詢，結果「測試查詢」回報「查到 11 個結果（有歧義）」——選了一個
理論上應該範圍夠窄的容器，結果查詢範圍完全沒有縮小，跟沒選容器時一樣。

**原因**：當時的模板寫法是：
```
//{ancestor.class}[.//*[@text="{錨點文字}" or @content-desc="{錨點文字}"]]//{el.class}[{目標條件}]
```
意思是「找一個{class}，這個{class}底下某處有錨點文字」——但 XPath 的
`//` 是搜尋**文件裡全部**符合條件的節點，不是只找「離錨點最近的那一個」。
如果這個 LinearLayout 本身還被包在**更外層、範圍更大**的其他 LinearLayout
容器裡（清單版面幾乎一定是這樣，外層還有 RecyclerView、頁面根容器等），
那些外層的 LinearLayout 因為「transitively（間接地）」也包含著這個錨點
文字（畢竟錨點文字本來就在它們的子孫節點裡的某處），一樣會符合
`.//*[@text=...]` 這個條件而被選中——查詢範圍實際上變成「所有包含這段
文字的LinearLayout的聯集」，其中包含了範圍大到涵蓋整個清單的那些，
在裡面找「刪除」按鈕當然又會撈到全部11個。

**解法**：改用 XPath 的 `ancestor::` 軸，直接從錨點節點本身出發往上找：
```
//*[@text="{錨點文字}" or @content-desc="{錨點文字}"]/ancestor::{ancestor.class}[1]//{el.class}[{目標條件}]
```
`ancestor::{class}[1]` 明確指定「從這個錨點往上數，最近的一個{class}」，
不會誤選到更外層同class但範圍過大的容器。**兩種寫法差一個字都不行，
語意完全不同，這次是靠實測「測試查詢」直接看到命中數量不對才抓到，
純看程式碼邏輯不容易發現。**

**實測結果**：修正後同樣選第1層，「測試查詢」正確回報「查到 1 個結果
（唯一，可以儲存）」。

**會不會再發生**：不會（邏輯已修正），但這是個值得記住的通用教訓：
XPath 的 `[.//condition]`（找「底下包含X的容器」）跟 `ancestor::X[1]`
（找「從某個錨點往上最近的X」）語意完全不同，前者常常會不小心選到範圍
過大的祖先節點，這種「消歧義」情境要用後者才對。

### 39. viewer_server.py：session 失效時的例外被內層邏輯默默吞掉，自動重連形同虛設（已修正）

**背景**：問題37功能開發完成、實測到一半時，`/inspect` 開始持續回報
「在目前畫面上找不到這個元件的線索」，即使確認手機畫面明明是對的。
排查花了不少時間，最後直接測 `/test_xpath` 一個最簡單的查詢才看到
真正的錯誤訊息：`InvalidSessionIdException: A session is either
terminated or not started`——原來是 `viewer_server.py` 常駐的 Appium
session 已經失效了（推測是本次除錯過程中，同時開了好幾支獨立的
Python 腳本連線去做別的操作，跟這支伺服器常駐的連線互相干擾/取代
導致的）。

**原因**：`do_POST()` 原本的設計是外層包一個 `try/except
InvalidSessionIdException`，抓到就重連再試一次——這個設計本身沒錯，
但 `inspect_element()`/`test_xpath()`，以及它們呼叫的
`run_test_case_android.py` 定位函式（`_locate_by_xpath` 等），內部
大多用「`try/except Exception` 廣泛捕捉、捕到就當作這個定位方式失敗、
换下一種方式試」的寫法——這個設計對「單一定位方式失敗」是正確、必要的
（本來就要能夠容忍某個方法失敗、繼續試下一個），但也連帶把
`InvalidSessionIdException` 一起吞掉、當成「查不到」處理，導致這個例外
永遠不會傳到 `do_POST()` 外層，自動重連邏輯完全沒有機會被觸發——回報
出來的訊息永遠是誤導性的「找不到這個元件」，看不出真正原因是連線失效。

**解法**：不依賴內層程式碼願不願意把例外往外拋，改成**每次請求最前面
主動探測**：新增 `ensure_session_alive()`，用一個查不到任何結果也沒關係
的輕量查詢（`find_elements(AppiumBy.ID, "__viewer_server_liveness_check__")`）
直接測試 session 是否還活著，抓到 `InvalidSessionIdException` 就立刻
重連，在 `do_POST()` 分派請求給實際處理函式**之前**先做，不管後面的
函式內部怎麼處理例外都不影響這一層的判斷。

**實測結果**：修正後重跑，session 存活/重連判斷正確運作，`/inspect`、
`/test_xpath` 都恢復正常回應。

**會不會再發生**：`ensure_session_alive()` 這個機制已經解決了「session
死掉但看不出來」這個根本問題，之後不會再誤導成「找不到元件」。但這次
排查也暴露一個使用習慣上的提醒：**同時間不要一邊讓 `viewer_server.py`
常駐執行、一邊又另外開獨立的 Python 腳本連線做別的操作**——
UiAutomator2 對同一台裝置的並行 session 支援不穩定，容易互相干擾，
需要對模擬器下操作時，優先透過 `viewer_server.py` 自己的 API
（`/tap` 等）進行，不要另開新連線。

### 40. 新功能：「🤖 AI定位」，讓 LLM 自動生成並驗證唯一定位的 XPath

**背景**：問題37做的「重新定義XPath」需要人工自己看上層元素、自己組查詢。
這次要求再加一個「交給AI做」的版本：把畫面完整tree跟目標元件的已知線索
一起丟給LLM，請它產生一個能唯一定位的XPath。

**設計核心：不是單次生成就相信，要驗證，不通過就回饋重試**——這是這次
明確要求的行為（「找到唯一xpath就修改上去，找不出來就顯示無法定位」），
跟人工流程「測試查詢通過才能存」是同一個精神，只是把「測試」這一步也
自動化、串成一個迴圈：

1. `viewer_server.py` 新增 `agent_generate_xpath()`：
   - 先用現成的 `_locate_best_effort` 盡力定位一次，找得到的話把它的
     即時座標當作「正確答案」基準（找不到也沒關係，這正是需要AI救援的

### 42. 「邊捲邊抓」補上橫向捲動收集，修正問題34（Android，已實測驗證）

**背景**：問題34當時記錄「已知限制、尚未修正」——`testapp_home` 有一個
「推薦專區（左右滑動）」橫向卡片列表，當時只有3張卡片，剛好初次渲染就

人工核對截圖跟清單，發現卡片已經增加到7張，但清單裡只有前3張——

**修正做法**：`capture_screen_map_android.py` 新增：
- `find_scrollable_regions(xml_source)`：找出畫面上所有
  `scrollable="true"` 的節點（class+bounds），不猜方向——Android
  accessibility tree 沒有可靠的方向屬性可讀
- `collect_horizontal_region()`：對其中一個候選容器原地嘗試「往右捲」，
  系統回報「沒有位移」就直接放棄（代表這其實是外層的垂直容器，不是真的

  容器在多輪垂直捲動裡重複出現時（y座標會變，故意不放進key）不會重複
  處理第二次
- 主收集迴圈 `collect_candidates_with_scroll()` 在每一輪垂直捲動之間，
  插入「這一輪畫面上有沒有還沒處理過的橫向容器」的檢查，有的話先把它
  收集完再繼續往下捲；重構出共用的 `_read_and_merge_round()` 讓垂直/
  橫向兩條收集路徑共用同一份 `merged`/`round_screenshots`，`_round_index`
  的追蹤機制不用另外特化

### 44. 測案執行 tap/input_text 後寫死 `time.sleep(1)`，App轉場/非同步載入較久時可能不夠

**背景**：使用者詢問「App實際可能會有延遲時間，執行時有需要特地寫延遲
幾秒嗎」，查證後發現這個疑慮是真實存在的風險：`run_test_case_android.py`/
`run_test_case.py`（CLI）跟 `viewer_server.py`/`viewer_server_ios.py`
（`/run_test_script`）這四個地方，`tap`/`input_text` 之後全部都只是寫死
`time.sleep(1)`。測試App自己就有一個轉場畫面刻意設計2秒的loading
（`Constants.TRANSITION_LOADING_MS = 2_000L`），已經超過這個固定1秒——
如果測案剛好點到會觸發轉場/非同步載入的按鈕，下一步很可能在畫面還沒
完成更新前就執行，容易誤判失敗或驗證到還沒更新的舊內容。

**解法**：這個專案在「掃描」階段其實已經處理過同一類問題——
`capture_screen_map_android.py`/`capture_screen_map.py` 的
`wait_for_screen_stable()` 不是猜一個固定秒數，而是輪詢畫面內容直到
連續兩次讀到的結果一致才判定穩定。把同樣的精神套用到「執行測案」階段：
新增 `wait_after_action(driver, max_wait=3.0, poll_interval=0.4)`
（兩個平台的 `run_test_case.py` 各自一份），輪詢 `page_source` 直到
連續兩次內容一致（穩定了）或到3秒上限為止才回傳，取代原本的
`time.sleep(1)`。時間上限刻意抓得比掃描時短（3秒 vs 掃描的~7.5秒），
避免被本來就不會停止變化的動態內容（跑馬燈、loading動畫）拖慢太多
測案執行時間。`viewer_server.py`/`viewer_server_ios.py` 的
`/run_test_script` 也改成呼叫這個函式，不再各自寫死睡眠。

**實測結果**：重跑先前驗證過的「設定頁改名稱→回首頁驗證問候語」
4步驟測案（改用「小華」這個新名稱，避免跟前次測試資料混淆），
**4/4步驟依然全部PASS**，整個HTTP請求（含3次tap/input_text的
自適應等待+4次實際定位操作）總耗時約7.3秒——如果照舊寫死
`time.sleep(1)`×3次，光等待就至少3秒，實測結果顯示改用自適應等待後
沒有變慢太多，同時多了「遇到真的需要更久時間的畫面時願意多等」的
彈性。

**會不會再發生**：任何有轉場動畫、非同步載入、網路請求的操作都可能
遇到，屬於一般性改善（不是單一App/單一情境限定）。**已知限制**：3秒
上限是依這次測試App的已知情境（2秒轉場）抓的經驗值，如果之後遇到
真實App有超過3秒的載入情境（例如真的網路API呼叫），會在時間到時就
放棄等待、繼續往下執行，可能還是會遇到同樣的誤判風險，屆時需要視情況
調高 `max_wait` 或評估是否要讓測試案例JSON支援每個step自訂等待時間
上限（這次沒有加這個欄位，先以「自適應等待取代固定猜測」這個核心改善
為主，避免一次改動範圍太大）。

### 45. 新功能：「改版比對Demo」新增人工套用（沿用舊ID＋更新屬性）

**背景**：延續前幾輪的討論——比對出「新版hash不同但其實是同一個真實
元件」時，該保留舊指紋還是換新指紋？結論是 `unique_id` 該當成穩定的
參照鍵（像資料庫primary key），不是「目前指紋的checksum」；它從來不是
拿去定位元件用的（定位靠的是`label`/`bounds`/`fingerprint.nearby_text`
這些內容欄位），所以「id跟目前指紋的hash對不起來」不是真正的問題，
只要人工判斷是同一個元件，保留舊id＋用新掃描的屬性值，兩者都能兼顧
（查表永遠查得到、定位永遠用最新內容）。使用者明確要求**不要在掃描
時自動寫回**，維持人工判斷、只在 `viewer.html` 的「改版比對Demo」
分頁加操作功能。

**做法**：
- 每張比對卡片（有舊版對應元件、且新版是`generated`來源時——native
  元件已經靠id完全相等自動confirmed，沒有需要套用的東西）新增
  「✅ 人工確認同一元件，套用舊ID」按鈕
- 點擊後：把**新版元件的 `unique_id`／`fingerprint` 換成舊版的**，
  其他屬性（`bounds`/`label`/`description`/`clickable`等）維持新版
  掃描到的最新值不動——這正是前幾輪討論定案的合併規則
- 套用狀態用一個獨立的 `Set`（`appliedMerges`）追蹤是哪個比對結果
  套用過，**刻意不直接在元件物件上加`_merged`之類的旗標欄位**，
  避免匯出的JSON多出一個不屬於原本schema的欄位、汙染資料格式
- 新增「📥 匯出套用後的新版JSON」按鈕，把套用後的完整新版
  `element_map.json`（所有畫面，不只比對的那個）匯出成檔案
- 比對頁面維持純文字/元件清單呈現，**沒有加任何截圖/圖片顯示**
  （這個分頁本來就沒有圖片上傳功能，維持現狀簡潔）

**實測結果**：用同一份 `element_map.json` 同時當舊版跟新版上傳
（構造一個「完全相同、必然100%匹配」的測試情境，驗證互動機制本身
對不對），選 `testapp_settings`（48個元件）執行比對，27個確定同一元件、
21個疑似需確認，正確出現29個套用按鈕（native id完全相同的那些正確地
沒有出現按鈕）。點擊其中一個generated元件的套用按鈕後，卡片正確變成
「✓ 已套用，新版unique_id/fingerprint已改為舊版的」，匯出按鈕從disabled
變成可點擊，點擊匯出沒有拋出錯誤，全程無 console 錯誤。

**會不會再發生**：這是常態功能，之後每次改版比對都會用到。

## `viewer.html` 新增功能：改版比對 Demo

在校對工具裡加了第二個分頁「改版比對 Demo」，把 PROJECT_BRIEF 決策3的
相似度計分規則（`class`必須相同、`label_text`相同+40分、`nearby_text`
高度重疊+25分／部分重疊最高+10分、`position_bucket`相同+20分、
`sibling_index`相同+10分，≥70確定同一元件／30~69需人工確認／<70全新元件）
用 JavaScript 實作了一版，純粹是**demo呈現用**，還沒有正式導入
`capture_screen_map.py` 的主流程（那邊還是「不同hash就當全新元件」的
簡單邏輯）。可以上傳新舊兩份 `element_map.json`、各自選畫面，執行比對後
會顯示每個新元件對應到哪個舊元件、分數多少、判定結果；如果額外上傳
舊版的測試腳本（`test_cases/*.json`），還會標註腳本引用的元件改版後
有沒有自動對應上，或需要人工複核。**這段 JS 邏輯之後如果要正式採用，
建議搬進 Python 主流程重新實作一次，確保跟掃描邏輯共用同一套規則，
不要讓 demo 版本跟正式版本的計分邏輯長期分岔。**

（測試時發現拿來比對的兩份資料剛好來自不同 App，比對出來的結果沒有意義——
這個功能的前提是「同一支 App、同一個畫面」改版前後的兩次掃描，之後拿
同一支 App 的資料重測即可看到有意義的結果。）

## 給下次接手的人的重點提醒

1. **一次性、跟 App 無關的設定**（1-4、8、9、11）：都已經解決，之後不太需要再處理，
   除非重灌開發環境或换 Mac。
2. **裝置層級、會重複發生的**（5、7）：換手機、或免費帳號 7 天效期到期時會再遇到，
   照上面步驟重做即可，不是程式或邏輯的問題。
3. **App 簽署身分相關**（6）：如果之後測試的目標 App 是用跟 WDA 不同的開發者帳號簽的，
   記得也要去手機上信任那個憑證。
4. **外部 API 隨機狀況**（10）：遇到 503 直接重跑就好，不用懷疑是自己設定錯。
5. **看到 exit code 1 先別急著判定失敗**（12）：檢查 `element_map.json` 有沒有存到資料，
   收尾階段的錯誤不代表掃描本身失敗。
6. **`PROJECT_BRIEF.md` 的 ID 格式表格已經跟實際程式碼不一致**（13）：
   `unique_id` 現在多了一段 `class`，記得跟原始交接文件的作者確認要不要同步更新文件。
7. **「有 native id」的判斷邏輯已經比原始版本嚴格**（14）：現在只有
   `name != label` 才算數，之前掃過的舊資料（例如第一版 `login_screen`）
   可能把「文字回填」誤判成 native id，建議都重掃一次更新。
8. **Gemini API 呼叫已加上自動重試**：遇到 503 會自動等待重試（最多4次，
   間隔遞增 5/10/15/20秒），不用再手動重跑指令，除非重試次數都用完才會真的報錯。
9. **候選元件範圍已擴大到純圖示（`XCUIElementTypeImage`）**（15）：這類元件
   會多一道 LLM 視覺判斷（`is_likely_interactive`）才決定收不收錄，目前沒有做
   尺寸粗篩，圖片多的畫面 LLM 成本會偏高，是刻意先求完整、之後再優化的取捨。
10. **捲動清單元件超出截圖範圍不會再讓程式崩潰**（16）：會優雅跳過裁切，
    `screenshot_crop` 存 `null`，但描述品質可能較差（LLM看不到那塊區域）。
11. **429 配額用盡是另一種完全不同的錯誤**（17）：跟503無關，是免費帳號
    每日請求數上限（目前20次/天/模型），換一組新 key 或等配額恢復才能解決，
    不會被自動重試機制誤判重試。
12. **unique_id 已加上碰撞後綴保底**（18）：指紋本身還是有機率碰撞
    （尤其重複排版結構的畫面），根本解法留給問題3一起處理。
13. **掃描前務必先截圖確認畫面內容**（19）：App 閒置逾時會自動登出，
    同名畫面重掃會覆蓋掉舊資料，養成「先截圖確認、再執行掃描」的習慣。
14. **`run_test_case.py` 執行前會先做畫面校驗**（22）：過半數 native 元件
    在目前畫面找不到就會中止執行，避免座標點擊備援機制誤觸別的畫面。
    執行測試腳本前一律先手動導航到正確畫面，不要依賴這個機制事後補救。
15. **`enabled=false` 的元件目前還是會被點擊並回報 PASS**（23）：
    `run_tap()` 還沒檢查元件是否真的可互動，這是已知但尚未修的落差。
16. **`generate_test_case.py`/`run_test_case.py` 目前只完整驗證過1個畫面**
    （`foolife_policy_overview`）：PROJECT_BRIEF 第二、三步驟的核心流程
    已經跑通，但涵蓋的情境還不夠廣，之後找更多不同類型的畫面（尤其是
    混合較多 generated 元件、或有 input_text 情境的畫面）多驗證幾次。
17. **`viewer.html` 的「改版比對 Demo」是純前端 JS 實作，還沒進主流程**：
    要正式採用得搬進 Python 重新實作一次，兩邊邏輯目前是分開的。
18. **指紋不穩定有4種真實成因，不是只有理論**（24）：動態文案/數值、
    非同步載入時機、`sibling_index`脆弱、LLM視覺判斷不穩定，前兩種靠
    問題25的輪詢機制緩解，`sibling_index`那種要等問題3的根本修正，
    LLM判斷不穩定目前沒有解法。
19. **掃描前會自動輪詢等畫面穩定**（25）：只解決「暫時性」的非同步載入
    問題，對動態文案/輪播banner沒有效果（那些內容本來就會一直變，
    輪詢再久也不會穩定，屬預期行為）。留意輸出的 `screen_stable_at_scan`
    欄位，`false` 代表這次資料需要人工複核。
20. **Android版 resource-id 不保證同畫面唯一**（26）：清單/網格類畫面
    幾乎一定會有多個項目共用同一個 resource-id（版型內部id），
    `capture_screen_map_android.py` 已加上同畫面重複偵測+自動降級成
    fingerprint 比對，但如果之後 iOS 版也遇到類似情況（同一個
    accessibilityIdentifier 出現在多個元件上），目前 iOS 版**沒有**
    這道防護，需要另外補上同樣的邏輯。
21. **Android版 Accessibility Tree 只反映當下實際渲染的內容，跟 iOS 不同**
    （27）：捲動清單裡沒顯示出來的元件，Android 上**掃描抓不到**（要先
    捲到那個位置才抓得到），iOS 上即使沒顯示，Tree 還是抓得到座標
    （已知問題16）。連帶地，`verify_current_screen()` 畫面校驗如果剛好
    抽查到的 native 元件都是不受捲動影響的頭尾固定列（標題列/底部導覽列
    這種常見版面），會在捲動位置根本不對的情況下依然回報「100%吻合」，
    是尚未修正的校驗盲區，執行測案前建議留意畫面本身是否有捲動內容。
22. **執行測案時，捲動內容裡的元件已加上自動捲動定位**（28）：Android
    用 `UiScrollable.scrollIntoView`、iOS 用 `mobile: scroll toVisible`，
    兩邊 API 不同是因為卡住的環節不同（Android是「查不到，因為節點還沒
    被建出來」，iOS是「查得到但不可互動」）。這個修正讓問題27校驗盲區
    的實際風險降低（後續步驟會自動捲到對的位置，不會默默SKIP），但校驗
    本身還是沒修，兩者要分開看。
23. **Android版已拿掉 `is_likely_interactive` 判斷**（29）：Android的
    `clickable`/`checkable`屬性本身就可靠，不需要像iOS那樣用LLM猜「像不像
    可以點擊」，這個判斷之前還誤把`ALWAYS_KEEP_CLASSES`（TextView）收錄的
    純文字元件排除掉。已修正，**這則筆記已被問題30取代**：後續兩平台都
    改成掃描端完全不過濾。
24. **掃描端已改成「全部收錄」，篩選責任移交 viewer.html**（30）：兩平台
    的 class 白名單/clickable判斷/`is_likely_interactive` 全部拿掉，只要
    節點有畫出來、座標合法就收錄。元件數量會比舊版資料明顯多（多了版面
    容器），這是預期行為不是bug。`viewer.html`「元件校對」分頁新增
    id來源/class/原始屬性（clickable/checkable/enabled/accessible，依
    資料動態出現哪些欄位）的篩選介面。舊格式（沒有這些新欄位）的
    `element_map.json` 資料依然能正常開啟，篩選介面會自動只顯示資料裡
    實際存在的欄位選項。
